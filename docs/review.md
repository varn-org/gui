# 🔬 Review

A full read of the project looking for what can kill it, what is left over, and where the three renderers disagree. Every item says what is wrong, what proves it, and what closes it. An item closes only when it is built, exercised by a test and described in the documentation.

All sixty-nine are closed, and a second read of the finished work found eight more, recorded in section F. Six of those were defects the first pass had shipped or left, and the one that mattered most would have left every icon and every canvas blank on the web. Eleven more defects were found while closing them, each by a test written to prove a fix and each recorded beside the item that led to it — the worst of those were a paragraph asked to run to two lines running to nine, a carousel of a few pages never leaving its first, and two runtimes in one process sharing one scheduler.

What this round is weakest on is written down in E14: six fixes are proven by a compiler and a careful reading rather than by a test, because each needs a finger or a real player. That is where the next round starts, and section F is the reason to take it seriously — a test that passes against a stand-in is not a test that the thing works.

Looking at the screens one by one found more still, in sections H and I, and the last of those was the layout costing a whole frame in a split view. Then the application was run on a real iPhone and section J found eight more, half of them things no screenshot can show: an animation, a navigation, a mode change and a file chooser. Running it again found four more, in section K, two of them introduced by that same round: a covered screen is held rather than shown, and the bar's trailing cell is not what a badge hangs off. Holding it a third time found that nothing arrived at all, which had been true since long before this review and is section L. A fourth round is section M, where the drawer refusing to close turned out to be `setState` unable to store false at all. A reader on the device then found four broken things in a row while every test passed, and section O is why: a test could report success for work that never ran. Then the gestures, and a turn of the phone, in section P. Then a tablet with a screen actually open, in section Q, which is also where the numbers reported for section I are corrected.

## A. What can kill or freeze a running application

- [x] **A1. A lifecycle callback that throws takes the application with it, and its siblings never mount.** `Runtime:commit` runs the build under `pcall` and then calls `runCallbacks(pending)` **outside** it. Those callbacks are `onMount`, `onUpdate` and `onLayout`, none of which is wrapped. Proven: two children, the first with an `onMount` that throws — `gui.start` raises, `onProblem` is never told, and the second child's `onMount` never runs at all. What a component does on mount is not the runtime's to trust, exactly as a press handler is not.
- [x] **A2. A render that fails after the first frame is reported nowhere and the screen freezes.** `bridge.run` arranges every later commit as `async.spawn(function() runtime:commit() end)` with nothing catching it. Proven: the error reaches the engine's log, the coroutine dies, `onProblem` is never told, and the commit stays scheduled forever. A screen that stops moving with nothing said is the worst failure this project can have.
- [x] **A3. Measured, and not worth doing.** Changing one row of an eight-hundred-row tree: the whole commit takes 4.0 ms, of which `reindex` is 0.35 ms — under nine per cent, and the fill of `byId` itself is 0.15 ms of that. The rest of a commit is the layout walk, which visits every node by construction because it builds the layout tree, so a commit is O(the tree) whether the index is rebuilt or not. Making the index incremental would save around three per cent and would put the correctness of `byId` back in the hands of the diff, which is exactly where B1 and B2 came from. Left as it is, deliberately.

## B. What the crash and race sweep found

- [x] **B1. A rotation reconciles components it has already unmounted, and the whole commit is refused.** `Runtime:build` walks the dirty set and reconciles each node without asking whether it is still mounted. A resize marks every component dirty, so if a parent is reached first its re-render unmounts a descendant and emits `remove`, and the descendant is then reconciled anyway and emits `update` against ids that no longer exist. Reproduced: `resize(1100, 800)` on an adaptive component fails with `the batch touched node 3, which was never created`. It depends on hash order, so it comes and goes. Android throws out of a JNI callback and the process dies, the web throws out of a wasm callback, and iOS applies the batch up to the failing operation and abandons the rest — leaving the screen permanently half drawn, because the diff only ever sends what changed and nothing ever repairs it.
- [x] **B2. The restyle and the repaint walk an index that predates the removals in the same batch.** Both iterate `byId`, which is rebuilt only after the batch has shipped, so every node unmounted in this commit still receives an `update` after its own `remove`. A dark-mode toggle or a remote picture arriving in the same frame as a list scrolling is enough. Same three outcomes as B1.
- [x] **B3. A picture that cannot be fetched is fetched again forever.** A failure is recorded in a table whose only reader has no callers, so the next commit re-enters the fetch, whose failure schedules another commit. Reproduced: one unreachable image is one request plus one full-tree commit per round, indefinitely. An application opened offline never stops.
- [x] **B4. A component that answers a different element type is never reattached.** The replace path reads `node.parent` and `node.index`, and a node carries `parentNode` and nothing else. Both are always nil, so the insert never fires: the old node is removed, the new one is created, and it is never put anywhere. The region goes blank permanently and the orphan stays in every renderer's view hierarchy forever. This is the ordinary "spinner while loading, content when done" shape. Same defect as C2, now with a reproduction.
- [x] **B5. Keyboard reveal is dead after the first state change.** The layout returns only the frames that actually moved, and the runtime keeps that as if it were the whole map. Reproduced: after mount the map has 42 entries and reveal works, after one ordinary `setState` it has **none**, and focusing a field under a 336pt keyboard produces no scroll at all. The partial case is worse than the empty one, since it scrolls to an offset summed from whichever ancestors happened to move. The keyboard test passes only because it never commits after mounting.
- [x] **B6. A throw inside a commit silently loses every component that had not been reached yet.** The dirty set is taken and cleared before the loop, so a render that fails at node *k* drops *k+1..n* — their state was already changed, so they render stale until something unrelated marks them dirty again. Reachable from a missing bundle image, an unknown theme token, a host that answers `null` to a measurement, and a `renderItem` that answers nothing.
- [x] **B7. A `setState` from inside a render is dropped rather than deferred.** `schedule` returns early while a commit is running without recording that a commit was asked for, so the node sits in the dirty set with nothing scheduled. On a screen where nothing else happens it never renders again.
- [x] **B8. Every `async.spawn` in the framework is unguarded, and a throw in one stops the loop for that tick.** The commit driver itself, a Toast's dismiss handler, the carousel's autoplay reaching a list that is no longer mounted, the picture cache's write, and `Presence` sleeping on a fractional duration, which raises because the engine takes an integer.
- [x] **B9. Caches that only ever grow.** Text measurements are keyed on the text itself and a clock that ticks adds an entry a second forever. The web's picture store holds a base64 copy of every image for the life of the process. Node extents are keyed by an id that only ever increases. iOS keeps a refresh reporter per surface with a `forget` nothing calls, and the web arms a scroll-settle timer it never clears on removal, so it fires for a node that is gone.
- [x] **B10. On the web a picture is read from disk with an await in the middle of a commit.** Reached from the style pass, it either raises `attempt to yield from outside a coroutine` — swallowed, so the browser is handed an engine path it cannot open and the image never appears — or it genuinely yields mid-commit, and every `setState` in that window is dropped by B7.
- [x] **B11. Two more of the same shape.** A demo's poll has no re-entrancy guard where both its siblings have one, so every press starts another permanent timer. A digest name is written in lower case in one place and upper in another, and the portable driver matches exactly, so the first remote image throws on a build without TLS.
- [x] **B12. Small ones that are still crashes.** A canvas path with fewer than two numbers indexes out of range on iOS. The web measures against `document.body` without checking it exists, and its own headless document has none. A non-numeric line height measures as `NaN`, which is a number, so it passes the guard and spreads through every frame in the tree.

## C. Dead code, leftovers and unused declarations

- [x] **C1. The reference and the promise test each know seven families, and the library exports nine.** `Presence` and `SplitView` are in neither list, so neither appears in `docs/components.md` and neither has a single prop checked. That is exactly how `SplitView.onShowingChange` — a declared event nothing anywhere fires — survived. One list, read by both.
- [x] **C2. A component whose root child changes type is never reattached.** `gui/diff.lua` reads `node.parent` and `node.index` to emit the `insert`, and a retained node only ever carries `parentNode`. Both are always nil, so the branch is unreachable and the operation is never sent. Dead code hiding a real defect.
- [x] **C3. A node type no component produces is still built.** `refresh` is gone from Lua, and both phone factories still build a view for it. The web would already throw on it, which is what proves it unreachable.
- [x] **C4. `Icon.family` is honoured by nobody**, and the promise test misses it because its substring match hits `font.family` in the font-registration path. The check compares whole names.
- [x] **C5. Unused locals.** `BAR` in `gui/components/containers.lua` and in `sample/app.lua`, both left behind when the bar became the platform's own.
- [x] **C6. Module exports nothing reads.** `element.marker`, `ref.metatable`, `protocol.version`, `protocol.operations`, `gui.element`, `chrome.rows`/`chrome.row` (asserted only by a test written for them), `pictures.Store:missed` — which makes its `failed` table write-only — and `Bridge:require`.
- [x] **C7. Dead assignments, and one of them was hiding a bug.** `child.parent`, `line.free` and `environment.size` are gone. `surface.height` is not a dead assignment at all — it is part of the context a component reads — but the guard above it compared only the width and the breakpoint, so a change that moved only the height returned early and left it stale. The guard now reads what it writes.
- [x] **C8. `Box:outerMain` takes a parameter every one of its four callers passes as nought.**
- [x] **C9. Logic written more than once.** One list of the types that scroll, read by both the layout and the runtime. One `support.cover`, which the four places that filled the surface each wrote out. One scrim, which the drawer had hand-rolled beside the presentation family's. The bar height each of them declared for itself is gone with the hand-rolled bar. Along the way `gui.components()` turned out to count every key a family module exports, so a helper exported beside the components read as one — it now counts what declares itself, which is what the reference page is built from, so the two lists cannot disagree.
- [x] **C10. Documentation claiming what is gone or wrong.** Closed with E1 to E11 below, and the two pages it named are gone.

## D. Where the three renderers disagree

- [x] **D0. The test that was built to catch this cannot catch it.** It checks each renderer separately now, and a name only counts as read where a renderer could actually be reading it: not in a table keyed by node type, not in the factory that chooses a view for one, and not in the type a component names itself after. Each of those was giving a prop a pass against a row that had nothing to do with it, and `Button.icon` survived all three. What it found is closed below.
- [x] **D0a. The twelve props and events that nothing kept.** Six were built on the web (`ActivityIndicator.animating` as a drawn spinner, `Avatar.initials`, `Slider.thumbColor`, `Switch.offColor` and `thumbColor`, `TextInput.placeholderColor`), which needed a stylesheet the renderer installs, since a placeholder, a range thumb and a switch's track are pseudo-elements that nothing can reach from script. Five were built on Android (`Pressable.hitSlop` through a delegate that carries every child that asked for it, `onPressIn` and `onPressOut` through the one touch a view answers, `Switch.offColor` as the second state of the one tint list, `Video.rate`). `Carousel.loop` and `SplitView.onShowingChange` were declared and built by nobody, and both now do what they say. `Button.icon` and `Chip.icon` were dropped rather than built: both already take children, and an `Icon` as a child works on all three today.
- [x] **D0b. A carousel of a few pages never moved off its first one.** The page it is on is read from the scroll offset, and that offset is only recorded when the realised window moves, which on a carousel whose every page is already realised is never. Its dots, the index it reported and the page it played to were all stuck at one. Found by the test written for `loop`. `gui/tools/promises.lua` concatenates all four source roots into one corpus and asks whether *anything* reads a prop, so a prop honoured by exactly one renderer passes. Every item below is invisible to it by construction. It checks each renderer separately, and a prop honoured by fewer than three is a failure naming which ones are missing. This is what closes the rest of the section and keeps it closed.
- [x] **D1. A radio reports nothing on Android or the web.** `onSelect` is bound on iOS only. `RadioGroup` is built entirely on `Radio.onSelect`, so radio groups are dead on two platforms out of three.
- [x] **D2. Typing into a `TextArea` never reaches Lua on iOS.** `onChange` is bound by casting to `UIControl`/`UITextField`, and a textarea is a `UITextView`, which is neither. Its focus events are wired, so only the change is missing.
- [x] **D3. An icon drew on one platform out of three, and the design was the cause rather than a missing branch.** A name resolved to an SF Symbol, which is a set iOS has and nobody else does, so `name` could not be honoured elsewhere at all. The engine now owns the set: `gui/style/icons.lua` carries thirty-four icons as runs of points, `Icon` draws them onto a `canvas`, and every renderer already draws one. There is no `icon` node type any more, `family` is gone with the platform sets it named, and the navigation bar's back mark is drawn rather than written as a character — each platform still chooses which mark, a chevron on iOS and an arrow on Android and the web.
- [x] **D4. A canvas is never drawn on the web.** `commands` has no branch at all.
- [x] **D5. A checkbox and a radio have no label on the web.** The renderer writes `textContent` onto an `<input>`, which is a void element and shows nothing.
- [x] **D6. An avatar is blank on the web.** `initials` has no branch.
- [x] **D7. Every elevated surface is flat on Android.** There is no shadow code anywhere in that renderer, so `Card.elevation`, `Sheet`, `Alert`, `ActionSheet`, `Menu` and `Drawer` all lose the thing that separates them from the page.
- [x] **D8. A rounded box has square corners on Android.** `overflow` has no case and nothing sets `clipToOutline`, so a round `Avatar` and a rounded `Card` are square there.
- [x] **D9. The committed value of a slider is lost on the web.** `onCommit` maps to the `change` event but `payload` has no branch for it, so the handler is given an empty table instead of the number.
- [x] **D10. A date and a time reported three different things, and the value read back in was a fourth.** A picker chooses what a calendar or a clock shows, not a moment on a timeline: reporting it as an instant gives it a zone nobody chose, and reading it back in another one moves the day. All three now report `"2026-09-05"` and `"09:30"`, which is what the control actually chose, and take the same form back — the web already refused the instant form on the way in, and Android ignored an incoming value entirely. A conformance case covers it in all four suites.
- [x] **D11. An event that carries nothing carries `{}` on the web.** Every other payload-less event sends `null` on the phones and a truthy empty table on the web.
- [x] **D12/D13. The web had no animation at all, which is worse than either of these said.** `transition`, `enter` and `exit` all fell through `applyProp` and were ignored, so every sheet, alert, drawer and screen change was instant on the web while both phones moved. The web now reads the same timing the phones do — a duration, a delay and four control points, which is exactly what `cubic-bezier` takes — and animates opacity and the transform alone, never the position or the size a frame carries. A node given a state to arrive from is put on screen in it and moves to the one it settles at a frame later, once, which is what the phones do.
- [x] **D14. Pull to refresh does nothing on the web.** Neither `refreshing` nor `onRefresh` is read there.
- [x] **D15. A carousel does not page on Android or the web.** `paging` is honoured on iOS only.
- [x] **D16. A press reports no edges on Android.** `onPressIn` and `onPressOut` are bound on iOS and the web only.
- [x] **D17. A long press fires two or three times on iOS.** The recogniser reports on `began`, `changed` and `ended` rather than once.
- [x] **D18. `numberOfLines` was undone twice on iOS, and the second one was worse than this said.** Applying a style wrote the default over what the prop had set, and then the frame operation overwrote it again with a count worked out from the height, which always follows. A paragraph told to run to two lines ran to nine. A count the tree asked for is a caller's decision and neither a style nor a frame may take it back.
- [x] **D19. The same paragraph is a different height on the web.** Its measurement uses a line height of 1.35 where the phones use the font's own, so the layout itself differs between platforms.
- [x] **D20. Android's video honours only the last of `muted`, `volume` and `loop`.** Each calls `setOnPreparedListener`, and each overwrites the one before it. Props arrive in no order, so which one survives is chance.
- [x] **D21. A plain `ScrollView` reported no scrolling on iOS, because it was a second scrolling view.** `VarnScrollView` was `VarnCollectionView` with the events left off, which is also the duplication C9 names. It is gone: one scrolling surface serves every scrolling type, which is what Android already did and says so in the same words.
- [x] **D22. A colour picker works only on the web.** Android builds a plain box for it, and iOS reports its change with a null payload.
- [x] **D23/D24. Every style field is now honoured by all three or is not promised at all.** Built: `fontStyle`, `letterSpacing`, `lineHeight` and `textDecoration` on the phones, real weights and `textAlign = "justify"` on Android, and `avatar` padding on the web. Each went in where the font is built, which is the one place both the drawing and the measurement read, since a string measured without what it is drawn with is measured as something the reader never sees. Dropped: `skewX` and `skewY`, because Android's view system has no shear and they could only ever have worked on two out of three; `textTransform`, because changing the case of a string is one call in Lua and a field for it would have to be applied in six places; and the four separate corner radii, which nothing wrote and nobody drew.
- [x] **D23a. A measurement was named by less than what changes it.** Neither phone's measurement cache counted the spacing or the line height in its key, so the same string measured at a different spacing answered the first measurement again. Android also never counted the tracking into the width at all, so a label was given a frame narrower than the text it went on to draw. Found by the conformance case written for D23, which now covers all four renderers.
- [x] **D25. Imperative actions refuse differently.** All three now raise the same named refusal: `scrollTo` on a node that does not scroll, `play` or `pause` on a node that is not a video. Android was the worst of the three, since it fell through to `View.scrollTo`, which scrolls a view's own content and is a different thing entirely.
- [x] **D26. A renderer decides things the engine is meant to decide.** `color` on a control was the real one, and it was worse than this said: a style's colour is the colour of a string, and a control that draws a tick, a spinner or a bar draws it in a colour of its own, which **all three** took from the platform's accent and none of them read. `Checkbox.color`, `Radio.color`, `ActivityIndicator.color` and `ProgressBar.color` now reach the mark on every platform. The Android span path also defaulted to a font size of 16 against 15 everywhere else. What is left is not a decision the engine could take: a `SeekBar` is positioned by whole numbers, so a step-less slider has to be divided into something, and a thousandth of the travel is finer than the track has pixels; a pull threshold and a scroll settle belong to the surface that has the gesture, and iOS reads its own from `UIRefreshControl` for exactly that reason.
- [x] **D27. Props declared and honoured by nobody at all.** `Button.icon`, `Chip.icon`, `Icon.family`, `DatePicker.mode = "datetime"`, `Picker.placeholder`, `Avatar.source`, `Avatar.badge`, `Checkbox.color`, `Radio.color`, `ActivityIndicator.color`, `ProgressBar.color`, `WebView.scrollEnabled`, `Checkbox.indeterminate`. Each is built or it is not declared.

## F. What a second read found, after the first was called finished

The first pass closed all sixty-nine. Reading it again with the question "what did I not check" found eight more, six of them defects the first pass had shipped or left.

- [x] **F1. Every canvas and every icon would have been blank on the web.** The bitmap was sized from the element's own box, and props are applied before the frame that gives the element a size, so it was drawn into nothing and never drawn again. The web test passed because a fake canvas has no size to be wrong about. It is sized from the frame the engine sent, and a frame redraws it.
- [x] **F2. The check that keeps a declaration honest excused any prop the engine mentioned.** The engine *reading* a prop is not the engine *answering* it: the layout reads how many lines a paragraph may run to in order to size its box, and a renderer still has to cut it off at the last one. A host's prop is now checked against all three renderers, and the ones the engine genuinely answers are written out by name with the reason, so each is a decision rather than an accident of grep. Asking the strict question surfaced the next five.
- [x] **F3. A paragraph never truncated on the web.** `numberOfLines` had no branch there at all, on `Text` or `RichText`.
- [x] **F4. A radio reported nothing on the web.** `onSelect` was bound on neither, so a `RadioGroup` was dead there — the same defect D1 fixed on Android, on the platform D1 did not name.
- [x] **F5. A carousel did not page on the web**, which D15 had fixed on Android and named as iOS-only.
- [x] **F6. Android had the twin of D18 and nobody had looked.** The frame operation overwrote `maxLines` with a count worked out from the height, exactly as iOS did. Android also honoured neither `thickness` on a bar nor `display` on a picker.
- [x] **F7. `DatePicker.mode` was read by nothing at all.** `mode = "datetime"` did nothing on any platform. It is gone rather than built: a `DatePicker` picks a date and a `TimePicker` picks a time, and a combined mode would have brought back the instant-shaped value D10 removed.
- [x] **F8. Two of my own fixes disagreed with the phones.** The web reported a chosen radio with no payload where both phones send a boolean, and a paging surface read the axis from a prop that had not arrived yet — the ordering invariant the project already states. Both were caught by the tests written for F4 and F5.

## G. What looking at the screen found

Everything above was found by reading and by tests. None of it found what a person saw in the first ten seconds of using the application.

- [x] **G1. A screen was left displaced for good whenever a commit landed during a transition.** `UIView.frame` is undefined while a view carries a transform — UIKit works one out through the other — and the engine animates a transform on every screen change while writing frames on every commit. A commit landing inside those 220 ms moved the view permanently, by however far the animation had travelled: exactly the forty points a `slideLeft` translates. It is rare, because it needs the two to coincide, and it is why half a screen was drawn off the left edge. A view is placed by its bounds and its centre now, which mean the same thing whatever the transform is. `EventTests` puts a transform on a view, sends a frame and fails at `x = -40` without the fix. Android lays out by edges and the web writes `left` and `top`, so neither has it.
- [x] **G2. The fix for G1 stopped every list scrolling, and that was mine.** A scrolling view's `bounds.origin` **is** its content offset, so writing a zero origin put every list back to the top on every commit — a list that would not scroll and shook. Only the size is written now. The test scrolls a list, sends a frame, and fails at `0` instead of `600` without it.
- [x] **G3. The system bars were a different colour from the bar under them.** Measured on the simulator: the strip behind the clock was `#17171d` and the navigation bar below it `#0b0b0f`, meeting at a hard edge, and the same at the bottom. `SafeArea` is a Lua component now: it paints the two strips the system draws over with `barStyle`, so a bar runs all the way up, and says how the system draws its own content over them with `barContent`. The strips are the tree's, so all three agree. What the system draws over them is the platform's own — `preferredStatusBarStyle` on iOS, the window's bar appearance on Android, the page's colour scheme on the web.
- [x] **G4. Reading and testing are not looking.** Every one of these passed every suite in this repository. The first was found by a person with the application in their hand, and the second by them again a minute after it shipped. `python3 run.py shots` and a real device are not optional extras next to the suites — they see a different class of defect entirely.

## H. What a screen-by-screen look found

Section G was found by a person holding the application. This is what came of going through every screen with the pictures in front of me, which is what should have happened first.

- [x] **H1. A rotation rendered the whole tree on every frame, and that was mine.** `Runtime:setInsets` had no guard where `setKeyboard` right below it has one, so every inset the platform reported rendered the tree again and invalidated every layout node. A platform animates its insets through a rotation, so that was every frame of one. It returns early when nothing changed now, and reading the surface is tracked so a change to it renders the components that read it rather than all of them. Measured after: a rotation still costs 11.9 ms a frame against a 16.7 ms budget, which is the layout itself and is not this item. Three attempts at that — not invalidating the generation, caching resolved styles, rendering selectively — each moved it by under half a millisecond, so the cost is the layout walk itself, which is I8. Closing that took a rotation frame to 7.1 ms.
- [x] **H2. A fixed column sat above every row it belonged to.** Written as one `and`/`or`, the layout's cross size read a child's **width** whenever that child declared no height, so a table's fixed column was centred against 64 in a row of 44 and placed at `y = -10`. Every value in the column was drawn between two rows. The layout test fails at `-10` without the fix. This is the engine, not the table: any child of a row with a width and no height had it.
- [x] **H3. A badge showed the number it was told to hide.** The ceiling was worked out for the measurement and never for what crossed the bridge, so a renderer was handed `value` and `max` and drew the raw number: `128` where the tree said `99+`. The count is written out once, in the engine. The badge also stretched to the width of whatever held it, since nothing said it should not.
- [x] **H4. A title was drawn over the way back.** The navigation bar stacked absolutely positioned children — the title at a fixed inset, the way back sized by the previous screen's name — so the two overlapped whenever either was long. The bar is a row now, and flex reserves space for each part: the title is cut off at the last letter that fits, and the way back yields before the title does. It also gains a trailing slot, which is what an application needs so its own buttons stop floating over everything.
- [x] **H5. A shopping bag was drawn over every menu and sheet.** With nowhere in the bar to put it, the sample had positioned it over the whole navigation stack. It sits in the bar's trailing slot now.
- [x] **H6. A tab's badge moved with the number of tabs.** Placed at a share of the tab's width, it sat over the label rather than beside it. The label and its badge are one box now, so the badge hangs off the corner of the word.
- [x] **H7. A list inside a scrolling view had to be given a height, and had been given 320.** The podcast home stopped a third of the way down with dead space under it. What holds a list can grow without end, so a list inside one needs a number, and a number written into a screen is wrong on every other device. The page is one list with everything above it as its header.

## I. The sweep after the screen-by-screen look

- [x] **I1. The same `and`/`or` broke the main axis too.** `mainSizeOf` read `row and child.width or child.height`, so a child of a row that declares only a height was laid out that many points **wide**: a box forty points tall came out forty wide. Both axes are read with an `if` now. The layout test fails at `40` without it. Every `x and y or z` in `gui/` was checked, and these two were the only ones where the middle value can be nil.
- [x] **I2. `Runtime:rerender` was dead.** Tracking who reads the surface replaced both of its callers, and what was left called only itself. Gone.
- [x] **I3. Seven overlays are now proven by touching them.** `apps/ios/UITests/OverlayUITests.swift` opens a modal, a sheet, an alert, an action sheet, a toast, a menu and a drawer, presses each one into existence and reads what it holds. None of them had ever been looked at: a screenshot shows the state a screen opens in, and every one of these is a thing a person has to touch before it exists at all.
- [x] **I4b. One runtime could render a component another runtime holds.** What reads the surface is remembered on the context, which is declared once for the whole process, so tracking readers handed a runtime components belonging to any other that was running. Marking one of those dirty puts a node in a tree that does not contain it, and the batch that follows names ids the renderer it reaches never created — the same crash B1 was. A runtime now takes only the readers born under its own scheduler. Two runtimes in one process is what the suite does on every file, which is exactly where this would have fired.
- [x] **I4c. The safe area's strips and the bar content had no test.** Both are covered now: the strips cover the insets the platform reported and nothing when the bars were not asked about, and the browser's colour scheme follows `barContent`.
- [x] **I4. Two of those failed, and both were the test rather than the application.** A row that carries a name of its own is an accessibility element in its own right, so the text inside it is not exposed separately and `app.staticTexts["Duplicate"]` finds nothing. Nearly reported as a defect in `Menu` and `ActionSheet`. What the test asks for is any element with that name now, which is what the press already did.

- [x] **I5. A rotation cost 11.9 ms a frame against a 16.7 ms budget, and now costs 10.1.** The profile put it in the layout rather than anywhere it had been looked for. `readEdges` built a property name by concatenating strings four times per edge, three properties per box, every pass — the hottest line in the engine, and the names are worked out once now. Reading the axis is a field on the box rather than a call. Two methods that existed to be called once each are the expression they answered.

  What was tried and measured at nothing: not invalidating the generation on a resize, caching resolved styles by the table they were written as, and caching the insets on the box — that last one was **slower**, because a rotation rebuilds every box and the cache is filled more often than it is read. Rendering only what reads the surface was kept because it is right, not because it was faster.

- [x] **I6. The premise was wrong, and measuring it found the real one.** A rotation does **not** hand the engine a new size on every frame: UIKit sets the model bounds to the final size at once and animates the presentation layer, so a full turn to landscape and back produces **four** surface reports. Counted from the simulator's own log. There was nothing to fix in the host contract, and the benchmark that said 10 ms a frame was measuring something that never happens.

  What does happen is **scrolling**, and it was the freeze. A scroll event cost **4.9 ms in portrait and 11.1 ms in landscape** — over half a frame before UIKit does anything, and worse the more rows fit, which is exactly what was reported.

- [x] **I7. A second remembered answer made the layout three times faster and wrong, and it is withdrawn.** Sizing a container asks each child for its size and asks again once it has handed out a share, so a box is asked two questions a pass and the memo could only hold the last. Holding both made a scroll cost 3.0 ms in landscape against 11.1.

  It is unsound. Everything a box holds is worked out during that box's own layout, so answering an older question hands back the right size while the boxes below it still hold what some other question produced. A box 101 wide, holding a plain box, holding one string: laid out at a few sizes and back, the string keeps the 40 points it would have measured on its own instead of stretching to 101. Three lines of tree.

  Found by property: forty trees of random shape, each laid out at five sizes, compared against a copy of the same tree that had never been laid out at all. The memo the engine shipped with passes that. Mine failed it 18 times, and my first two attempts to blame the old code were both invalid — the experiment checked one slot while writes still alternated between two.

  A relaxation that is sound — a leaf may answer either question, since what it measured is the whole of its answer — buys nothing measurable, so it is not there either. The layout is back to what it was, and `gui/tests/layout_test.lua` now holds the property, which is the lasting part of this.

- [x] **I8. A scroll event costs 4.7 ms in portrait, 10.5 ms in landscape and the whole frame budget in a split view, and there is roughly an order of magnitude of waste in it.** Counted on the gallery's long list, twenty scroll commits in landscape: **104 boxes in the tree, 3,214 layouts per commit** — thirty-one per box — and the busiest boxes are worked out **a hundred times each in one commit**. Across those commits each was asked only a dozen distinct questions, so most of that work is a question already answered.

  Three memos were written before the shape of the problem was clear, and all three were withdrawn. Each failed the same way and the failure named the cause: a box that answers from memory is never laid out, and a layout leaves more behind than a size. What a caller reads afterwards is `box.pass`, which says whether a frame has to be sent, and the state of everything below the box.

  What ships is two memos, split along exactly that line.

  A leaf keeps its last eight answers and any of them may be given again, since a leaf holds nothing below it. Answering one still runs `record`, so the box is left as a real layout would have left it, `pass` included. Worth about 13% on its own.

  A container keeps its last eight answers too, but hands one back **only to the pass that is asking how large it is**. Sizing a container asks every child its size, shares out what is left and then lays each child out for the share it was given, so the asking never decides where anything below the child sits and the layout that follows it is what puts the subtree in agreement. An answer given there therefore touches nothing but the size, leaves `laid` and `pass` alone, and cannot survive the layout that follows. This is the one that mattered: a subtree was being walked twice per level, so a tree cost what it held raised to its own depth.

  What a box remembers also has to be thrown away, and forgetting that was the fourth failure. A box is rebuilt with an empty memo when it changes, but a box **above** one that changed is not rebuilt, and it was keeping answers taken before the change — a row staying the width of the label it used to hold. `build` already marks those boxes as no longer laid out, and it clears their remembered answers in the same place now, since both are the same thing. Two hundred random trees with one leaf grown: eighty-nine of them kept a stale size before, none after.

  Measured on the gallery's long list, sixty scroll commits over 122 nodes: **2,615 real layouts per commit falls to 773**, and a scroll event costs

  | | before | after |
  |---|---|---|
  | phone, portrait | 4.26–4.54 ms | 3.00–3.13 ms |
  | phone, landscape | 9.23–9.34 ms | 3.61–4.10 ms |
  | split view, 1024×768 | 14.64–15.01 ms | 5.60–6.04 ms |

  Three interleaved rounds, since a single pair of runs on a warm machine says less than it looks like it does. The split view was spending nine tenths of a 60 Hz frame in the layout before UIKit had drawn anything, which is what a person feels as a list that will not keep up with a finger. It is a third of that budget now.

  Soundness is what the first three attempts lacked and what the fourth got wrong in a new way, so it is held by two property tests rather than by an argument. `gui/tests/layout_test.lua` lays sixty random trees out at ten sizes that come back around and compares every frame against a copy that has never been laid out at all, some of those boxes scrolling, since a box that scrolls asks its children something no other box asks. Run outside the suite over eighteen thousand trees at six seeds, every frame matched. The second lays a tree out, grows one leaf and lays it out again against a tree built with that leaf already grown, which is the shape a screen actually has: it holds still and its contents change. A hand-written version of that case was written first and passed against the defect, because the row it measured was being stretched by its parent and so answered the container's width rather than its own — the random trees are there because a case chosen by hand tests what its author already thought of.

## J. What a round on a real iPhone found

Eight defects, every one of them from holding the device rather than from reading the code or looking at a screenshot. Four are things a still image cannot show at all — an animation, a navigation, a mode change, a file chooser — which is the reason this section exists. Closing them found three more, each recorded beside the item that led to it: every icon re-sending its drawing on every commit, an arrival drawn before the node had a frame, and two tests in the suite pinning a defect as if it were the contract.

- [x] **J1. The file and image picker chooses nothing, on any platform.** `gui.FilePicker` declares `props = { "title" }` and `events = {}`, so there is no event a chosen file could ever be reported through — the component cannot work, by construction, whatever the renderers do. And they do nothing: iOS maps `filepicker` to `VarnChooserButton`, which is the `UIMenu` dropdown that `Picker` uses, so it opens a menu of options it does not have. Android maps it to a bare `Button` with no listener. Only the web builds a real `<input type="file">`, and nothing reads what it produces. It declares `kind`, `accept`, `multiple` and `maxBytes` now, and reports `onPick` with an array of `{ name, size, type, bytes }`. Behind it: `PHPickerViewController` for pictures and `UIDocumentPickerViewController` for everything else on iOS, `ACTION_OPEN_DOCUMENT` on Android, the file input on the web.

  Two decisions worth writing down. **The bytes cross as base64 rather than a path**, because the wasm build exports no filesystem to its host, so a path the engine could read is not something the browser can produce — and one renderer answering differently is the disagreement this whole review is about. **Nothing is written to disk**, because where a chosen file belongs is the application's to decide and inventing a cache for it would be a policy the framework has no business holding. `maxBytes` is there because a video read whole is a string no device should be asked to build: anything over it arrives named and measured but unread, which is a case a reader can be told about.

  On Android the chooser is not opened by the renderer. An activity's result belongs to the activity that started it, and a renderer holding one leaks it on a rotation, so the request goes up through `VarnGUIHost.onChoose` and comes back through `chose`, exactly the way the back press already does.

- [x] **J2. The navigation title is not centred, it is centred in what is left over.** The bar is a flat row of back button, title and actions, and the title cell is `grow = 1` between them, so its centre is the centre of the gap rather than the centre of the bar. With a back button reading `Varn GUI` and no actions, the title sits visibly right of centre — which is what the screenshot shows. Apple centres the title on the bar and lets the leading item give way first, truncating the back label to its chevron before the title loses a character. The bar is three cells now, the leading and trailing ones each `grow = 1, basis = 0` so they claim the same width, and the trailing one is there holding nothing precisely so that they can. `gui/tests/chrome_test.lua` measures the title's middle against the bar's for three lengths of back label and for a bar carrying an action: it is 161 of 195 without the fix and within a point of centre with it.

- [x] **J3. Switching from dark to light left white content on a white bar.** `barContent` is whatever the tree hardcoded — the sample says `light` and never changes it — so after the appearance switched to light the status bar was still drawing light glyphs onto a bar that had turned white. Nothing was readable. The answer turned out to be that a screen should say nothing at all. Every platform already draws its own bars from the appearance — `.default` on iOS means exactly that — so a tree that names nothing follows light and dark for free, and naming one pins it for both. The sample says nothing now, `barContent` is documented as the override it is, and the gallery is guarded by a test that fails if anything pins it again.

  The iOS side also kept `VarnSystemBars.wanted` in a global static that no unmount cleared, so a screen that had gone still decided what was drawn over the one that replaced it. The request belongs to a `VarnSafeAreaView` now and is given up when that view is released, which survives the renderer moving a view between parents in a way that giving it up on leaving a superview would not.

- [x] **J4. The carousel's dots are only on the first slide.** `Dots` is appended to the carousel's own children, which are the scrolling content, so the indicator scrolls away with page one and every later page has none. The dots are a sibling over the surface now, so a carousel is a box holding the scrolling surface and the indicator rather than the surface alone. Two more things were wrong and are fixed with it: it drew one dot per entry with no cap, so forty pages drew forty dots wider than the phone, and it is a window of at most seven that travels with the page being read. The note about the safe area was wrong — the dots sit inside the carousel's own box, not against the bottom of the screen.

- [x] **J5. Every list draws a scrollbar, and on the carousel it ruins it.** iOS sets `showsVerticalScrollIndicator` **and** `showsHorizontalScrollIndicator` from one prop regardless of which way the surface actually scrolls, so a vertical list shows a horizontal bar it has no use for. Android already reads the axis and iOS does not. A paged carousel should never show one at all — it says where it is with its dots. On the web `scrollbarWidth` was the only thing set, which Safari ignores, so `showsIndicator = false` did nothing there.

  iOS reads the axis now, and because the axis and the indicator arrive in no order both are held on the view and the pair is worked out again whenever either lands. A carousel defaults to drawing none, since it says where it is with its dots. The web marks the element and a rule in the sheet takes the bar away on `::-webkit-scrollbar` as well as through `scrollbar-width`, so both engines obey.

- [x] **J6. The table's sort order is a text character glued to the title.** `column.title .. " ⌃"`, inside a `numberOfLines = 1` Text, so the mark is the first thing a long column title truncates away, and the glyph is whatever the platform's font has for U+2303 — a different shape and a different size on each of the three. It is a drawn `chevron-up` or `chevron-down` beside the title now, so the title truncates without taking the mark with it. The accordion had the same defect and the same fix, and so did the two chevrons in the sample's own rows.

  Closing it surfaced a defect of its own: an icon's `commands` were compared by identity, so every icon on screen re-sent its whole drawing on every commit. The index grew twenty chevrons and started sending thirteen operations for a render that changed nothing. `commands`, `spans`, `options` and `segments` are compared by value now, the way a style already was.

- [x] **J7. A modal arrives with no animation and leaves by dragging the whole screen down.** It appears in one frame, and on dismissal the scrim goes down with the panel, so the background is uncovered from the top while the overlay is still on its way out. The cause is that the scrim and the panel are one node inside one `Presence`, animated by one transition: `slideUp` moves everything it holds, the scrim included, and moves it forty points rather than off the screen. They are two different moves — a scrim fades, a panel travels the whole of its own height — and they are two now: every presented component is a fading ground holding a travelling panel, and `Presence` honours the style it is given so the panel is the node that moves rather than a screen-sized sheet of glass with the panel somewhere inside it.

  A travel of a panel's own height cannot be written in the tree, since only the layout knows what the panel turned out to be, so `translateX` and `translateY` take a percentage as well as a number and every renderer reads it against the node it is moving. That exposed the cause of the other half: the arrival was drawn when the node was **created**, before it was ever given a frame, so a percentage resolved to nothing and there was no geometry to animate from. It waits for the frame now, on iOS and Android both.

  The action sheet lost its two hardcoded offsets with this — its choices and its way out are one panel stacked from the bottom edge rather than two absolutely placed boxes that each had to know how tall the other was.

- [x] **J8. Every screen is rebuilt when it is returned to, so nothing survives a navigation.** `NavigationStack` renders `screens[index]` and nothing else, keyed by the screen, so pushing unmounts everything underneath and popping mounts a new instance of it. Every `setState`, every scroll offset a list is holding, and every half-typed field is gone on the way back. UIKit keeps the whole stack alive and shows the top of it, and that is what it does now: every screen up to the index is rendered, the top one in the flow and the rest exactly where they were, covered and taking no touches. A screen that is still there is also what a push has to slide over.

  Two tests in the suite were pinning the old behaviour — one asserting the screen beneath must not be built, one that the index gives up the screen — and both were pinning the defect. They assert the new contract now, and the test that matters is a new one: type into a field, push a screen over it, come back, and the field still holds what was typed.

  It costs what keeping the stack alive costs. A scroll event on the gallery's long list goes from 5.7 ms to 6.5 ms in a split view, which is the covered screen being walked, and is still well under half of what it was before I8.


## K. What the second round on the device found

Four more, and two of them were mine — introduced by J8 and J2 in the round above. A covered screen showing through is the clearest lesson in the whole review: a change that is right in principle is not finished until it has been held.

- [x] **K1. A screen pushed over another one let it through, so three screens were legible at once.** J8 kept every screen in the stack alive and left them visible, on the reasoning that a screen is opaque and that a push has to slide over something. Neither holds. A screen is not required to paint a background — the shop's product page does not — so the grid underneath drew its own rows through the product's price, and pushing again put the checkout over the bag over the grid. A covered screen is held rather than shown now: it keeps its place, its state and its scroll offset, and it is not drawn and takes no touches. What a reader sees is the top screen and nothing else.

- [x] **K2. The grid drew its columns edge to edge.** `spacing` went into the row height and nowhere else, so a two column grid gave each column exactly half the width and the halves touched. A share worked out with the gaps taken off first is a length and a percentage at once, which a style cannot say, so each column keeps its share and holds its content half a gap in from each side it has a neighbour on — which is a whole gap between two of them and the grid's own padding at the outer edges.

- [x] **K3. Three controls were drawn with their padding twice.** A badge, a chip and a tooltip each declared it once as what the type is naturally worth and again in the style the renderer draws it with, and the engine added both. A badge showing a single digit came out 32 by 24 for a pill that is 20 by 20, hanging off whatever it was counting and covering the thing beside it. A chip reading `Tag` was a hundred points wide.

  The style is the single source, since it is what the renderer insets the text by, and `natural.padding` is gone from all three. Two defects fell out of fixing it. `natural.sizeOf` returned nothing at all for a declaration carrying only a minimum, so a chip lost the 44 it is never shorter than the moment its padding was taken out. And a natural minimum was applied to the **text** rather than to the box, which is the padding over again — a badge's `minWidth = 20` means the pill is twenty across, not that the digit inside it is.

- [x] **K4. Any rightward swipe anywhere closed the screen, and it closed before the finger was lifted.** The back gesture was a `UISwipeGestureRecognizer` over the whole surface with `direction = .right`. It took a drag on a checkbox, a slider or a carousel as a request to leave, and a swipe recogniser fires the moment the movement passes its threshold, so the screen went while the finger was still down. It is a `UIScreenEdgePanGestureRecognizer` on the leading edge now, acted on when the gesture ends, and only when the drag went far enough or fast enough — which is what the system asks of the same gesture.

- [x] **K5. On Android a finger passed straight through into a box that was told to take none.** `pointerEvents = "none"` set `isClickable = false`, which stops the box and nothing inside it, where iOS stops the whole subtree and the browser does too. It only started to matter with K1 — a covered screen is made of exactly this, so the screen underneath would have kept answering the press meant for the one over it. The box refuses to dispatch now, which is what makes a finger pass through rather than be swallowed: the platform carries on to the next sibling, the same as the other two.

## L. What holding it a third time found

Two reports, one cause underneath them, and the cause had been there since long before this review.

- [x] **L1. Nothing arrived. Every overlay, drawer and pushed screen appeared in a single frame, while the way out of them animated correctly.** `reusable` compared a node with the one it replaces on its **type alone**, and a component's own root is compared with nothing else — there is no key lookup above it, the way there is among siblings. So a component that says it is showing something else by changing the key was patched in place rather than replaced. `Presence` works exactly that way: `absent` becomes `present`, and the node it produced was reused, so it was never created, so `enter` was never applied and there was nothing to arrive from. Leaving animated correctly because that is a style applied to a node that already exists. A key is what says two nodes of the same type are different things, and it now counts wherever the node sits.

  A second defect was hiding behind it, and only became reachable once arrivals worked. A node is framed again in the commit after the one that creates it, and the frame re-resolved the transform from the style so that a travel written as a share of the node could follow a change of size. A node arriving carries its travel in `enter`, not in its style, so re-resolving from a style that names none reset it to nothing — wiping the state the arrival was to come from, a frame before it ran. Only a transform the style actually names is written there now.

- [x] **L2. The drawer did not come in from its side.** It was L1: the panel travels the whole of its own width from the edge it is anchored to, and none of that was applied because the node was never created. Both sides are the caller's to choose and the demo shows each of them now.

## M. What a fourth round on the device found

Seven reports, and the first of them uncovered a defect in the core that had been silently wrong for the whole project: state could not be set to false.

- [x] **M1. The drawer opened and would not close.** `setState` was written `self.state[key] = value ~= none and value or nil`. False is the middle of an `and`/`or` and Lua takes the other branch for it, so **every state a screen set to `false` was stored as nothing at all**. It reads as false everywhere except against false itself, which is exactly where it surfaced: a drawer asking `state.drawer ~= false` got nil, answered true, and stayed open. This is the same `x and y or z` defect the layout had twice, in the one place where it reaches every application written on the engine. It is an explicit `if` now.

  The headless renderer had the identical line for a prop arriving in an update, so a control updated to false — a switch turned off, a checkbox unticked, anything made invisible — read back as nil. Every test asking whether a prop is false after an update was weaker than it looked, and the conformance suite runs against that renderer. The three real renderers compare explicitly and were right.

- [x] **M2. The progress screen ends in a box that says nothing.** `Skeleton { lines = 3 }` reserves the height of three lines and the renderers draw one flat rectangle, so it reads as a component left there by mistake rather than as text that has not arrived. A skeleton is lines, so it is one now: a component that stacks a shaded box per line with the last one short, the way the last line of a paragraph is. The box itself stays a host node, the way a badge's pill does.

- [x] **M3. The bar only moves when a button is pressed.** The demo has an `Advance` button, which shows a bar can be set but not what one looks like while something is happening. It fills on its own and starts again at the end, and says the percentage beside it.

  Making it do that found that a runtime could not be taken down at all. A repeating timer holds the engine's loop open, and every test that mounts a demo left it mounted, so the suite stopped terminating. `Runtime:stop` unmounts the tree, which fires every `onUnmount` and so ends every timer a screen had asked for — a host closing a surface had no way to do that, and nothing in the suite had ever needed one.

- [x] **M4. The resize modes cannot be told apart.** Every one of them draws `logo.png`, which is a plain blue rounded square — so `cover`, `contain`, `stretch` and `center` produce four identical squares and the screen demonstrates nothing. ## O. What the suite was not catching, and what it cost

This section exists because a reader on a device found four broken things in a row while every test passed. They were right to say the tests were not worth much, and the reason turned out to be structural rather than a matter of writing more of them.

- [x] **O1. A test could report success for work that never ran.** `async.run` schedules a body and returns — everything after an `await` in it runs once the chunk has ended, if it runs at all. ## P. Gestures, and a turn of the phone

- [x] **P1. A swipe was taken as a press, so scrolling past a row opened it.** Every platform tells a press from a swipe by how far the finger travelled, and none of the three renderers was doing it.

  On iOS a `Pressable` is a `UIControl`, and a control fires when a drag ends inside it however far it went — so a swipe across a row the width of the screen opened whatever the row was for. On Android a view only gives up a click when the touch leaves its **bounds**, which a swipe across a wide row never does, so it is held to `scaledTouchSlop` instead. On the web a `click` is raised whenever a pointer goes down and comes up on one element, however far it went between, so how far it went is watched on the surface and a press that travelled is not reported.

  Writing the Android test found that the fix reported the press ending **twice** — once where the finger was given up and again when it was lifted. One release, reported once.

- [x] **P2. - [x] **P3. Turning the phone lost everything a reader had put into the screen.** The engine keeps state across a resize — it was the tree above it that changed. Both are drawn: the stack keeps the screen that was left for as long as the move takes and hands it the state to travel towards, and `renderers/ios/tests/ChromeTests.swift` now proves the platform animates it rather than putting it there — the layer carries an animation of exactly the duration the tree asked for, and the view has travelled the whole way once it is over. Nothing about the arrival change touched it, since an exit is a style applied to a node that is already on screen.

- [x] **V2. Dead code, left-over constants and props nothing reads.** A round of changes leaves things behind: a constant whose rule was deleted, a helper nobody calls, a prop a renderer stopped honouring, a file nothing requires. The whole tree was swept for it: every local a module declares against what reads it, every export against what names it, every class and constant in the three renderers, and every Lua module against what requires it. Nothing was left behind, which is what the earlier rounds' habit of deleting the rule and its constant together bought.

- [x] **V3. Everything a renderer holds is given back.** A sound, a video, a map's tiles, a location receiver, a timer, an observer: each is opened by a node and has to be closed when that node goes, and a cell that is recycled goes and comes back. Android was closing them on **detaching**, which a recycled cell does on its way out of a list and undoes on its way back: a sound that scrolled off a screen never played again, and a map never drew another tile. Removal is the one moment that is right, and the renderer is what knows it — `VarnReleasing` is called from `remove`, detaching only stops the ticking, and `renderers/android/.../LifetimeTest.kt` holds both halves. On iOS what a node opened goes with the node, which `PlaceTests` proves by holding weak references to a player, a receiver and a map and finding all three gone. In a browser a media element taken out of the page carries on playing until it is collected, so it is stopped as it goes.

- [x] **V4. Nothing that runs off the main thread may touch a view that is gone.** A tile that arrives after the map was taken down, a fix reported after the screen was left, a player ticking into a view that has been released. Each hop was read: a tile arriving after the map was released is dropped, a permission a reader granted after the screen was left is ignored, a fix that came back late is not reported, and the pending posts are cleared as the map goes. The half of the component lifecycle that runs inside the diff is guarded the way the half after the batch already was, so a screen whose `onWillAppear` throws takes itself down and not the tree — `gui/tests/lifecycle_test.lua` builds a broken component beside a working one and finds both on screen with the failure reported.

- [x] **V5. Nothing in the engine may be left growing without a bound.** What a field remembers about what it said, what a list keeps about its cells, what a runtime holds for pictures, and what a demo keeps in module state rather than in the tree. What a field remembers about what it said is capped at sixty-four values on all three, which is what a commit could still be carrying rather than the whole of what was ever typed into it. The chat kept which conversations had been read in module state rather than in the tree, which is state that outlives the screen and belongs to nobody: it is component state now.

- [x] **V6. Whatever the sweep finds lands in this list and in `CLAUDE.md`.** A defect that is fixed and not written down is one the next round writes again.

## W. A second sweep, deeper than the first

- [x] **W1. A number json cannot carry crossed the bridge as nothing.** NaN and infinity both encode as `null`, which a renderer reads as no number at all and lays the node out at nowhere: a screen that vanishes with nothing said anywhere, which is the worst failure there is. A frame is checked before it is sent — the node keeps the frame it had and the problem is reported — and the runtime already did this for a measurement, so the boundary is consistent. `gui/tests/runtime_test.lua` builds a box whose width is a division by zero and finds it reported rather than drawn at nowhere.

- [x] **W2. Rendering a screen proved nothing about using one.** Every demo was rendered and none was used, so a handler that throws — a picture handed a prop it does not take, a payload read from nothing — passed every case in the suite and failed on the device. Every press and every change a reader can make is now made against every demo in `gui/tests/sample_test.lua`, with what the platform sends as the payload, and any problem reported while a demo is driven fails the suite naming the demo and the failure. It found one on its first run.

- [x] **W3. What the renderers still answered for a component that no longer exists.** `Avatar` became a component built from the others, and all three renderers were still handling `initials` for the node type it used to be, with the reference tool still listing three of its props as answered elsewhere. Every prop each renderer answers was checked against what something declares, and every prop applied without a type check was read: nothing else was left behind.

- [x] **W4. Anything that lands after the tree has been taken down.** A picture that arrives, a timer that fires and an event a host sends all come whenever they come, and a runtime with no tree left has nothing to commit: building one from a root that is not there reports a failure a reader can do nothing about, once for each thing still on its way. Every entry point a host or a callback can reach — `schedule`, `commit`, `dispatch`, `resize`, `setInsets`, `setAppearance`, `setKeyboard`, `setTheme`, `goBack`, `invalidatePictures`, `invalidateMeasurements` — answers nothing once the tree is down, and the test calls every one of them after stopping and finds nothing reported.

- [x] **W5. The store of pictures a run had fetched grew for ever.** The bytes it hands a renderer with no filesystem were already bounded, and what it remembered about which url landed in which file was not: a feed scrolling through thousands of pictures kept an entry for each of them for the life of the process. Both that and what it remembers about a picture it could not have are bounded caches now, and the file is still on disk once an entry is dropped, so a picture asked for again is found rather than fetched twice.

- [x] **W6. A contract implemented by four classes lived inside one of them.** `VarnSettling` and `VarnReleasing` were written in the map view that happened to need them first. They are in `VarnContracts.swift` and `VarnContracts.kt` now, which is where something four views implement belongs.

- [x] **W7. A host that stopped went on watching the page.** The browser host disconnected nothing when it stopped: a resize observer, a listener on what the reader set their device to and two on the visual viewport all went on reporting into an engine that had stopped answering. Everything it sets up is given back now — the observer is disconnected and the listeners are added against one signal that is aborted — and `renderers/web/tests/scrolling.test.js` counts them out as well as in.

## X. A third sweep, into the parts nothing had driven

- [x] **X1. A field on Android kept what it had said in a view tag, which is a crash waiting for a device.** `View.setTag(int, Any)` refuses any key that is not an application resource id and throws where it is given one, and the key was the hash of a string: whether it worked at all depended on the top byte of that hash, and the AAR has no resources to declare one with. - [x] **X2. Every one of them was put through the engine: none reported a problem and none produced a number that could not be sent.

- [x] **X3. Every event a reader can cause is now caused against every demo.** The driver pressed and changed, which left the handlers behind everything else untouched: what a list says when it is scrolled to its end, what a field says when the return key is pressed, what a row says when it is swiped, what a picker says when a file comes back, what a player says when it reaches the end. - [x] **X4. - [x] **X5. ## Y. A fourth sweep, at the edges of the platform boundary

- [x] **Y1. A failure inside the Android host unwound through the engine's own frame.** Everything a host registers is called from there, and the Android one let a throw out: a malformed batch, an unknown node type or a json failure would have taken the process rather than the screen. Each registered call answers the engine now and reports the problem, which is what the iOS host already did, so the two are the same shape.

- [x] **Y2. A field on Android reported every keystroke once per binding.** The text watcher was **added** rather than set, and a handler that comes and goes rebinds, so a field whose `onChange` was conditional grew a watcher each time it came back and reported each keystroke that many times — a tree fighting itself over what a reader typed. The field carries one watcher for its life and what it calls is swapped. Everything else that binds was read for the same shape: the browser removes before it adds, iOS detaches the reporter it replaces, and every other Android binding is a setter.

- [x] **Y3. The reconciler had never been fuzzed.** Reordering is where one goes wrong quietly: the tree is right, the renderer holds the same nodes, and a reader sees an order nobody asked for. Eighty random orders of five keyed rows are now drawn and read back through the frames, which is what catches an index that counts a sibling it should not.

- [x] **Y4. - [x] **Y5. Nothing the runtime holds grows across commits.** Four hundred commits of a screen of thirty rows leave the frames, the extents, the dirty set, the index by id and the measured controls exactly the size they were after the first one.

- [x] **Y6. `gui.stop` was not in the table of what a platform reports.** A host event nobody documented is one the next host forgets to send, which is a tree that never comes down. ## Z. A fifth sweep, and the loop that never ends

- [x] **Z1.
