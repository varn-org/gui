# 🔬 Review

A full read of the project looking for what can kill it, what is left over, and where the three renderers disagree. Every item says what is wrong, what proves it, and what closes it. An item closes only when it is built, exercised by a test and described in the documentation.

All sixty-nine are closed, and a second read of the finished work found eight more, recorded in section F. Six of those were defects the first pass had shipped or left, and the one that mattered most would have left every icon and every canvas blank on the web. Eleven more defects were found while closing them, each by a test written to prove a fix and each recorded beside the item that led to it — the worst of those were a paragraph asked to run to two lines running to nine, a carousel of a few pages never leaving its first, and two runtimes in one process sharing one scheduler.

What this round is weakest on is written down in E14: six fixes are proven by a compiler and a careful reading rather than by a test, because each needs a finger or a real player. That is where the next round starts, and section F is the reason to take it seriously — a test that passes against a stand-in is not a test that the thing works.

Looking at the screens one by one found more still, in sections H and I, and the last of those was the layout costing a whole frame in a split view. Then the application was run on a real iPhone and section J found eight more, half of them things no screenshot can show: an animation, a navigation, a mode change and a file chooser. Running it again found four more, in section K, two of them introduced by that same round: a covered screen is held rather than shown, and the bar's trailing cell is not what a badge hangs off. Holding it a third time found that nothing arrived at all, which had been true since long before this review and is section L. A fourth round is section M, where the drawer refusing to close turned out to be `setState` unable to store false at all. A reader on the device then found four broken things in a row while every test passed, and section O is why: a test could report success for work that never ran. Then the gestures, and a turn of the phone, in section P. Then a tablet with a screen actually open, in section Q, which is also where the numbers reported for section I are corrected.

## A. What can kill or freeze a running application

- [x] **A1. A lifecycle callback that throws takes the application with it, and its siblings never mount.** `Runtime:commit` runs the build under `pcall` and then calls `runCallbacks(pending)` **outside** it. Those callbacks are `onMount`, `onUpdate` and `onLayout`, none of which is wrapped. Proven: two children, the first with an `onMount` that throws — `gui.start` raises, `onProblem` is never told, and the second child's `onMount` never runs at all. What a component does on mount is not the runtime's to trust, exactly as a press handler is not.
- [x] **A2. A render that fails after the first frame is reported nowhere and the screen freezes.** `bridge.run` arranges every later commit as `async.spawn(function() runtime:commit() end)` with nothing catching it. Proven: the error reaches the engine's log, the coroutine dies, `onProblem` is never told, and the commit stays scheduled forever. A screen that stops moving with nothing said is the worst failure this project can have.
- [x] **A3. Measured, and not worth doing.** Changing one row of an eight-hundred-row tree: the whole commit takes 4.0 ms, of which `reindex` is 0.35 ms — under nine per cent, and the fill of `byId` itself is 0.15 ms of that. The rest of a commit is the layout walk, which visits every node by construction because it builds the layout tree, so a commit is O(the tree) whether the index is rebuilt or not. Making the index incremental would save around three per cent and would put the correctness of `byId` back in the hands of the diff, which is exactly where B1 and B2 came from. Left as it is, deliberately.

## B. What the crash and race sweep found

- [x] **B1. A rotation reconciles components it has already unmounted, and the whole commit is refused.** `Runtime:build` walks the dirty set and reconciles each node without asking whether it is still mounted. A resize marks every component dirty, so if a parent is reached first its re-render unmounts a descendant and emits `remove`, and the descendant is then reconciled anyway and emits `update` against ids that no longer exist. Reproduced: `resize(1100, 800)` on an adaptive component fails with `the batch touched node 3, which was never created`. It depends on hash order, so it comes and goes. Android throws out of a JNI callback and the process dies, the web throws out of a wasm callback, and iOS applies the batch up to the failing operation and abandons the rest — leaving the screen permanently half drawn, because the diff only ever sends what changed and nothing ever repairs it.
- [x] **B2. The restyle and the repaint walk an index that predates the removals in the same batch.** Both iterate `byId`, which is rebuilt only after the batch has shipped, so every node unmounted in this commit still receives an `update` after its own `remove`. A dark-mode toggle or a remote picture arriving in the same frame as a list scrolling is enough. Same three outcomes as B1.
- [x] **B3. A picture that cannot be fetched is fetched again forever.** A failure is recorded in a table whose only reader has no callers, so the next commit re-enters the fetch, whose failure schedules another commit. Reproduced: one unreachable image is one request plus one full-tree commit per round, indefinitely. An application opened offline never stops.
- [x] **B4. A component that answers a different element type is never reattached.** The replace path reads `node.parent` and `node.index`, and a node carries `parentNode` and nothing else. Both are always nil, so the insert never fires: the old node is removed, the new one is created, and it is never put anywhere. The region goes blank permanently and the orphan stays in every renderer's view hierarchy forever. This is the ordinary "spinner while loading, content when done" shape. Same defect as C2, now with a reproduction.
- [x] **B5. Keyboard reveal is dead after the first state change.** The layout returns only the frames that actually moved, and the runtime keeps that as if it were the whole map. Reproduced: after mount the map has 42 entries and reveal works, after one ordinary `setState` it has **none**, and focusing a field under a 336pt keyboard produces no scroll at all. The partial case is worse than the empty one, since it scrolls to an offset summed from whichever ancestors happened to move. The keyboard test passes only because it never commits after mounting.
- [x] **B6. A throw inside a commit silently loses every component that had not been reached yet.** The dirty set is taken and cleared before the loop, so a render that fails at node *k* drops *k+1..n* — their state was already changed, so they render stale until something unrelated marks them dirty again. Reachable from a missing bundle image, an unknown theme token, a host that answers `null` to a measurement, and a `renderItem` that answers nothing.
- [x] **B7. A `setState` from inside a render is dropped rather than deferred.** `schedule` returns early while a commit is running without recording that a commit was asked for, so the node sits in the dirty set with nothing scheduled. On a screen where nothing else happens it never renders again.
- [x] **B8. Every `async.spawn` in the framework is unguarded, and a throw in one stops the loop for that tick.** The commit driver itself, a Toast's dismiss handler, the carousel's autoplay reaching a list that is no longer mounted, the picture cache's write, and `Presence` sleeping on a fractional duration, which raises because the engine takes an integer.
- [x] **B9. Caches that only ever grow.** Text measurements are keyed on the text itself and a clock that ticks adds an entry a second forever. The web's picture store holds a base64 copy of every image for the life of the process. Node extents are keyed by an id that only ever increases. iOS keeps a refresh reporter per surface with a `forget` nothing calls, and the web arms a scroll-settle timer it never clears on removal, so it fires for a node that is gone.
- [x] **B10. On the web a picture is read from disk with an await in the middle of a commit.** Reached from the style pass, it either raises `attempt to yield from outside a coroutine` — swallowed, so the browser is handed an engine path it cannot open and the image never appears — or it genuinely yields mid-commit, and every `setState` in that window is dropped by B7.
- [x] **B11. Two more of the same shape.** A demo's poll has no re-entrancy guard where both its siblings have one, so every press starts another permanent timer. A digest name is written in lower case in one place and upper in another, and the portable driver matches exactly, so the first remote image throws on a build without TLS.
- [x] **B12. Small ones that are still crashes.** A canvas path with fewer than two numbers indexes out of range on iOS. The web measures against `document.body` without checking it exists, and its own headless document has none. A non-numeric line height measures as `NaN`, which is a number, so it passes the guard and spreads through every frame in the tree.

## C. Dead code, leftovers and unused declarations

- [x] **C1. The reference and the promise test each know seven families, and the library exports nine.** `Presence` and `SplitView` are in neither list, so neither appears in `docs/components.md` and neither has a single prop checked. That is exactly how `SplitView.onShowingChange` — a declared event nothing anywhere fires — survived. One list, read by both.
- [x] **C2. A component whose root child changes type is never reattached.** `gui/diff.lua` reads `node.parent` and `node.index` to emit the `insert`, and a retained node only ever carries `parentNode`. Both are always nil, so the branch is unreachable and the operation is never sent. Dead code hiding a real defect.
- [x] **C3. A node type no component produces is still built.** `refresh` is gone from Lua, and both phone factories still build a view for it. The web would already throw on it, which is what proves it unreachable.
- [x] **C4. `Icon.family` is honoured by nobody**, and the promise test misses it because its substring match hits `font.family` in the font-registration path. The check compares whole names.
- [x] **C5. Unused locals.** `BAR` in `gui/components/containers.lua` and in `sample/app.lua`, both left behind when the bar became the platform's own.
- [x] **C6. Module exports nothing reads.** `element.marker`, `ref.metatable`, `protocol.version`, `protocol.operations`, `gui.element`, `chrome.rows`/`chrome.row` (asserted only by a test written for them), `pictures.Store:missed` — which makes its `failed` table write-only — and `Bridge:require`.
- [x] **C7. Dead assignments, and one of them was hiding a bug.** `child.parent`, `line.free` and `environment.size` are gone. `surface.height` is not a dead assignment at all — it is part of the context a component reads — but the guard above it compared only the width and the breakpoint, so a change that moved only the height returned early and left it stale. The guard now reads what it writes.
- [x] **C8. `Box:outerMain` takes a parameter every one of its four callers passes as nought.**
- [x] **C9. Logic written more than once.** One list of the types that scroll, read by both the layout and the runtime. One `support.cover`, which the four places that filled the surface each wrote out. One scrim, which the drawer had hand-rolled beside the presentation family's. The bar height each of them declared for itself is gone with the hand-rolled bar. Along the way `gui.components()` turned out to count every key a family module exports, so a helper exported beside the components read as one — it now counts what declares itself, which is what the reference page is built from, so the two lists cannot disagree.
- [x] **C10. Documentation claiming what is gone or wrong.** Closed with E1 to E11 below, and the two pages it named are gone.

## D. Where the three renderers disagree

- [x] **D0. The test that was built to catch this cannot catch it.** It checks each renderer separately now, and a name only counts as read where a renderer could actually be reading it: not in a table keyed by node type, not in the factory that chooses a view for one, and not in the type a component names itself after. Each of those was giving a prop a pass against a row that had nothing to do with it, and `Button.icon` survived all three. What it found is closed below.
- [x] **D0a. The twelve props and events that nothing kept.** Six were built on the web (`ActivityIndicator.animating` as a drawn spinner, `Avatar.initials`, `Slider.thumbColor`, `Switch.offColor` and `thumbColor`, `TextInput.placeholderColor`), which needed a stylesheet the renderer installs, since a placeholder, a range thumb and a switch's track are pseudo-elements that nothing can reach from script. Five were built on Android (`Pressable.hitSlop` through a delegate that carries every child that asked for it, `onPressIn` and `onPressOut` through the one touch a view answers, `Switch.offColor` as the second state of the one tint list, `Video.rate`). `Carousel.loop` and `SplitView.onShowingChange` were declared and built by nobody, and both now do what they say. `Button.icon` and `Chip.icon` were dropped rather than built: both already take children, and an `Icon` as a child works on all three today.
- [x] **D0b. A carousel of a few pages never moved off its first one.** The page it is on is read from the scroll offset, and that offset is only recorded when the realised window moves, which on a carousel whose every page is already realised is never. Its dots, the index it reported and the page it played to were all stuck at one. Found by the test written for `loop`. `gui/tools/promises.lua` concatenates all four source roots into one corpus and asks whether *anything* reads a prop, so a prop honoured by exactly one renderer passes. Every item below is invisible to it by construction. It checks each renderer separately, and a prop honoured by fewer than three is a failure naming which ones are missing. This is what closes the rest of the section and keeps it closed.
- [x] **D1. A radio reports nothing on Android or the web.** `onSelect` is bound on iOS only. `RadioGroup` is built entirely on `Radio.onSelect`, so radio groups are dead on two platforms out of three.
- [x] **D2. Typing into a `TextArea` never reaches Lua on iOS.** `onChange` is bound by casting to `UIControl`/`UITextField`, and a textarea is a `UITextView`, which is neither. Its focus events are wired, so only the change is missing.
- [x] **D3. An icon drew on one platform out of three, and the design was the cause rather than a missing branch.** A name resolved to an SF Symbol, which is a set iOS has and nobody else does, so `name` could not be honoured elsewhere at all. The engine now owns the set: `gui/style/icons.lua` carries thirty-four icons as runs of points, `Icon` draws them onto a `canvas`, and every renderer already draws one. There is no `icon` node type any more, `family` is gone with the platform sets it named, and the navigation bar's back mark is drawn rather than written as a character — each platform still chooses which mark, a chevron on iOS and an arrow on Android and the web.
- [x] **D4. A canvas is never drawn on the web.** `commands` has no branch at all.
- [x] **D5. A checkbox and a radio have no label on the web.** The renderer writes `textContent` onto an `<input>`, which is a void element and shows nothing.
- [x] **D6. An avatar is blank on the web.** `initials` has no branch.
- [x] **D7. Every elevated surface is flat on Android.** There is no shadow code anywhere in that renderer, so `Card.elevation`, `Sheet`, `Alert`, `ActionSheet`, `Menu` and `Drawer` all lose the thing that separates them from the page.
- [x] **D8. A rounded box has square corners on Android.** `overflow` has no case and nothing sets `clipToOutline`, so a round `Avatar` and a rounded `Card` are square there.
- [x] **D9. The committed value of a slider is lost on the web.** `onCommit` maps to the `change` event but `payload` has no branch for it, so the handler is given an empty table instead of the number.
- [x] **D10. A date and a time reported three different things, and the value read back in was a fourth.** A picker chooses what a calendar or a clock shows, not a moment on a timeline: reporting it as an instant gives it a zone nobody chose, and reading it back in another one moves the day. All three now report `"2026-09-05"` and `"09:30"`, which is what the control actually chose, and take the same form back — the web already refused the instant form on the way in, and Android ignored an incoming value entirely. A conformance case covers it in all four suites.
- [x] **D11. An event that carries nothing carries `{}` on the web.** Every other payload-less event sends `null` on the phones and a truthy empty table on the web.
- [x] **D12/D13. The web had no animation at all, which is worse than either of these said.** `transition`, `enter` and `exit` all fell through `applyProp` and were ignored, so every sheet, alert, drawer and screen change was instant on the web while both phones moved. The web now reads the same timing the phones do — a duration, a delay and four control points, which is exactly what `cubic-bezier` takes — and animates opacity and the transform alone, never the position or the size a frame carries. A node given a state to arrive from is put on screen in it and moves to the one it settles at a frame later, once, which is what the phones do.
- [x] **D14. Pull to refresh does nothing on the web.** Neither `refreshing` nor `onRefresh` is read there.
- [x] **D15. A carousel does not page on Android or the web.** `paging` is honoured on iOS only.
- [x] **D16. A press reports no edges on Android.** `onPressIn` and `onPressOut` are bound on iOS and the web only.
- [x] **D17. A long press fires two or three times on iOS.** The recogniser reports on `began`, `changed` and `ended` rather than once.
- [x] **D18. `numberOfLines` was undone twice on iOS, and the second one was worse than this said.** Applying a style wrote the default over what the prop had set, and then the frame operation overwrote it again with a count worked out from the height, which always follows. A paragraph told to run to two lines ran to nine. A count the tree asked for is a caller's decision and neither a style nor a frame may take it back.
- [x] **D19. The same paragraph is a different height on the web.** Its measurement uses a line height of 1.35 where the phones use the font's own, so the layout itself differs between platforms.
- [x] **D20. Android's video honours only the last of `muted`, `volume` and `loop`.** Each calls `setOnPreparedListener`, and each overwrites the one before it. Props arrive in no order, so which one survives is chance.
- [x] **D21. A plain `ScrollView` reported no scrolling on iOS, because it was a second scrolling view.** `VarnScrollView` was `VarnCollectionView` with the events left off, which is also the duplication C9 names. It is gone: one scrolling surface serves every scrolling type, which is what Android already did and says so in the same words.
- [x] **D22. A colour picker works only on the web.** Android builds a plain box for it, and iOS reports its change with a null payload.
- [x] **D23/D24. Every style field is now honoured by all three or is not promised at all.** Built: `fontStyle`, `letterSpacing`, `lineHeight` and `textDecoration` on the phones, real weights and `textAlign = "justify"` on Android, and `avatar` padding on the web. Each went in where the font is built, which is the one place both the drawing and the measurement read, since a string measured without what it is drawn with is measured as something the reader never sees. Three were dropped instead. `skewX` and `skewY` went because Android's view system has no shear, so they could only ever have worked on two out of three. `textTransform` went because changing the case of a string is one call in Lua and a field for it would have to be applied in six places. The four separate corner radii went because nothing wrote them and nobody drew them.
- [x] **D23a. A measurement was named by less than what changes it.** Neither phone's measurement cache counted the spacing or the line height in its key, so the same string measured at a different spacing answered the first measurement again. Android also never counted the tracking into the width at all, so a label was given a frame narrower than the text it went on to draw. Found by the conformance case written for D23, which now covers all four renderers.
- [x] **D25. Imperative actions refuse differently.** All three now raise the same named refusal: `scrollTo` on a node that does not scroll, `play` or `pause` on a node that is not a video. Android was the worst of the three, since it fell through to `View.scrollTo`, which scrolls a view's own content and is a different thing entirely.
- [x] **D26. A renderer decides things the engine is meant to decide.** `color` on a control was the real one, and it was worse than this said: a style's colour is the colour of a string, and a control that draws a tick, a spinner or a bar draws it in a colour of its own, which **all three** took from the platform's accent and none of them read. `Checkbox.color`, `Radio.color`, `ActivityIndicator.color` and `ProgressBar.color` now reach the mark on every platform. The Android span path also defaulted to a font size of 16 against 15 everywhere else. What is left is not a decision the engine could take: a `SeekBar` is positioned by whole numbers, so a step-less slider has to be divided into something, and a thousandth of the travel is finer than the track has pixels. A pull threshold and a scroll settle belong to the surface that has the gesture, and iOS reads its own from `UIRefreshControl` for exactly that reason.
- [x] **D27. Props declared and honoured by nobody at all.** `Button.icon`, `Chip.icon`, `Icon.family`, `DatePicker.mode = "datetime"`, `Picker.placeholder`, `Avatar.source`, `Avatar.badge`, `Checkbox.color`, `Radio.color`, `ActivityIndicator.color`, `ProgressBar.color`, `WebView.scrollEnabled`, `Checkbox.indeterminate`. Each is built or it is not declared.

## F. What a second read found, after the first was called finished

The first pass closed all sixty-nine. Reading it again with the question "what did I not check" found eight more, six of them defects the first pass had shipped or left.

- [x] **F1. Every canvas and every icon would have been blank on the web.** The bitmap was sized from the element's own box, and props are applied before the frame that gives the element a size, so it was drawn into nothing and never drawn again. The web test passed because a fake canvas has no size to be wrong about. It is sized from the frame the engine sent, and a frame redraws it.
- [x] **F2. The check that keeps a declaration honest excused any prop the engine mentioned.** The engine *reading* a prop is not the engine *answering* it: the layout reads how many lines a paragraph may run to in order to size its box, and a renderer still has to cut it off at the last one. A host's prop is now checked against all three renderers, and the ones the engine genuinely answers are written out by name with the reason, so each is a decision rather than an accident of grep. Asking the strict question surfaced the next five.
- [x] **F3. A paragraph never truncated on the web.** `numberOfLines` had no branch there at all, on `Text` or `RichText`.
- [x] **F4. A radio reported nothing on the web.** `onSelect` was bound on neither, so a `RadioGroup` was dead there — the same defect D1 fixed on Android, on the platform D1 did not name.
- [x] **F5. A carousel did not page on the web**, which D15 had fixed on Android and named as iOS-only.
- [x] **F6. Android had the twin of D18 and nobody had looked.** The frame operation overwrote `maxLines` with a count worked out from the height, exactly as iOS did. Android also honoured neither `thickness` on a bar nor `display` on a picker.
- [x] **F7. `DatePicker.mode` was read by nothing at all.** `mode = "datetime"` did nothing on any platform. It is gone rather than built: a `DatePicker` picks a date and a `TimePicker` picks a time, and a combined mode would have brought back the instant-shaped value D10 removed.
- [x] **F8. Two of my own fixes disagreed with the phones.** The web reported a chosen radio with no payload where both phones send a boolean, and a paging surface read the axis from a prop that had not arrived yet — the ordering invariant the project already states. Both were caught by the tests written for F4 and F5.

## G. What looking at the screen found

Everything above was found by reading and by tests. None of it found what a person saw in the first ten seconds of using the application.

- [x] **G1. A screen was left displaced for good whenever a commit landed during a transition.** `UIView.frame` is undefined while a view carries a transform — UIKit works one out through the other — and the engine animates a transform on every screen change while writing frames on every commit. A commit landing inside those 220 ms moved the view permanently, by however far the animation had travelled: exactly the forty points a `slideLeft` translates. It is rare, because it needs the two to coincide, and it is why half a screen was drawn off the left edge. A view is placed by its bounds and its centre now, which mean the same thing whatever the transform is. `EventTests` puts a transform on a view, sends a frame and fails at `x = -40` without the fix. Android lays out by edges and the web writes `left` and `top`, so neither has it.
- [x] **G2. The fix for G1 stopped every list scrolling, and that was mine.** A scrolling view's `bounds.origin` **is** its content offset, so writing a zero origin put every list back to the top on every commit — a list that would not scroll and shook. Only the size is written now. The test scrolls a list, sends a frame, and fails at `0` instead of `600` without it.
- [x] **G3. The system bars were a different colour from the bar under them.** Measured on the simulator: the strip behind the clock was `#17171d` and the navigation bar below it `#0b0b0f`, meeting at a hard edge, and the same at the bottom. `SafeArea` is a Lua component now: it paints the two strips the system draws over with `barStyle`, so a bar runs all the way up, and says how the system draws its own content over them with `barContent`. The strips are the tree's, so all three agree. What the system draws over them is the platform's own — `preferredStatusBarStyle` on iOS, the window's bar appearance on Android, the page's colour scheme on the web.
- [x] **G4. Reading and testing are not looking.** Every one of these passed every suite in this repository. The first was found by a person with the application in their hand, and the second by them again a minute after it shipped. `python3 run.py shots` and a real device are not optional extras next to the suites — they see a different class of defect entirely.

## H. What a screen-by-screen look found

Section G was found by a person holding the application. This is what came of going through every screen with the pictures in front of me, which is what should have happened first.

- [x] **H1. A rotation rendered the whole tree on every frame, and that was mine.** `Runtime:setInsets` had no guard where `setKeyboard` right below it has one, so every inset the platform reported rendered the tree again and invalidated every layout node. A platform animates its insets through a rotation, so that was every frame of one. It returns early when nothing changed now, and reading the surface is tracked so a change to it renders the components that read it rather than all of them. Measured after: a rotation still costs 11.9 ms a frame against a 16.7 ms budget, which is the layout itself and is not this item. Three attempts at that — not invalidating the generation, caching resolved styles, rendering selectively — each moved it by under half a millisecond, so the cost is the layout walk itself, which is I8. Closing that took a rotation frame to 7.1 ms.
- [x] **H2. A fixed column sat above every row it belonged to.** Written as one `and`/`or`, the layout's cross size read a child's **width** whenever that child declared no height, so a table's fixed column was centred against 64 in a row of 44 and placed at `y = -10`. Every value in the column was drawn between two rows. The layout test fails at `-10` without the fix. This is the engine, not the table: any child of a row with a width and no height had it.
- [x] **H3. A badge showed the number it was told to hide.** The ceiling was worked out for the measurement and never for what crossed the bridge, so a renderer was handed `value` and `max` and drew the raw number: `128` where the tree said `99+`. The count is written out once, in the engine. The badge also stretched to the width of whatever held it, since nothing said it should not.
- [x] **H4. A title was drawn over the way back.** The navigation bar stacked absolutely positioned children — the title at a fixed inset, the way back sized by the previous screen's name — so the two overlapped whenever either was long. The bar is a row now, and flex reserves space for each part: the title is cut off at the last letter that fits, and the way back yields before the title does. It also gains a trailing slot, which is what an application needs so its own buttons stop floating over everything.
- [x] **H5. A shopping bag was drawn over every menu and sheet.** With nowhere in the bar to put it, the sample had positioned it over the whole navigation stack. It sits in the bar's trailing slot now.
- [x] **H6. A tab's badge moved with the number of tabs.** Placed at a share of the tab's width, it sat over the label rather than beside it. The label and its badge are one box now, so the badge hangs off the corner of the word.
- [x] **H7. A list inside a scrolling view had to be given a height, and had been given 320.** The podcast home stopped a third of the way down with dead space under it. What holds a list can grow without end, so a list inside one needs a number, and a number written into a screen is wrong on every other device. The page is one list with everything above it as its header.

## I. The sweep after the screen-by-screen look

- [x] **I1. The same `and`/`or` broke the main axis too.** `mainSizeOf` read `row and child.width or child.height`, so a child of a row that declares only a height was laid out that many points **wide**: a box forty points tall came out forty wide. Both axes are read with an `if` now. The layout test fails at `40` without it. Every `x and y or z` in `gui/` was checked, and these two were the only ones where the middle value can be nil.
- [x] **I2. `Runtime:rerender` was dead.** Tracking who reads the surface replaced both of its callers, and what was left called only itself. Gone.
- [x] **I3. Seven overlays are now proven by touching them.** `apps/ios/UITests/OverlayUITests.swift` opens a modal, a sheet, an alert, an action sheet, a toast, a menu and a drawer, presses each one into existence and reads what it holds. None of them had ever been looked at: a screenshot shows the state a screen opens in, and every one of these is a thing a person has to touch before it exists at all.
- [x] **I4b. One runtime could render a component another runtime holds.** What reads the surface is remembered on the context, which is declared once for the whole process, so tracking readers handed a runtime components belonging to any other that was running. Marking one of those dirty puts a node in a tree that does not contain it, and the batch that follows names ids the renderer it reaches never created — the same crash B1 was. A runtime now takes only the readers born under its own scheduler. Two runtimes in one process is what the suite does on every file, which is exactly where this would have fired.
- [x] **I4c. The safe area's strips and the bar content had no test.** Both are covered now: the strips cover the insets the platform reported and nothing when the bars were not asked about, and the browser's colour scheme follows `barContent`.
- [x] **I4. Two of those failed, and both were the test rather than the application.** A row that carries a name of its own is an accessibility element in its own right, so the text inside it is not exposed separately and `app.staticTexts["Duplicate"]` finds nothing. Nearly reported as a defect in `Menu` and `ActionSheet`. What the test asks for is any element with that name now, which is what the press already did.

- [x] **I5. A rotation cost 11.9 ms a frame against a 16.7 ms budget, and now costs 10.1.** The profile put it in the layout rather than anywhere it had been looked for. `readEdges` built a property name by concatenating strings four times per edge, three properties per box, every pass — the hottest line in the engine, and the names are worked out once now. Reading the axis is a field on the box rather than a call. Two methods that existed to be called once each are the expression they answered.

  What was tried and measured at nothing: not invalidating the generation on a resize, caching resolved styles by the table they were written as, and caching the insets on the box — that last one was **slower**, because a rotation rebuilds every box and the cache is filled more often than it is read. Rendering only what reads the surface was kept because it is right, not because it was faster.

- [x] **I6. The premise was wrong, and measuring it found the real one.** A rotation does **not** hand the engine a new size on every frame: UIKit sets the model bounds to the final size at once and animates the presentation layer, so a full turn to landscape and back produces **four** surface reports. Counted from the simulator's own log. There was nothing to fix in the host contract, and the benchmark that said 10 ms a frame was measuring something that never happens.

  What does happen is **scrolling**, and it was the freeze. A scroll event cost **4.9 ms in portrait and 11.1 ms in landscape** — over half a frame before UIKit does anything, and worse the more rows fit, which is exactly what was reported.

- [x] **I7. A second remembered answer made the layout three times faster and wrong, and it is withdrawn.** Sizing a container asks each child for its size and asks again once it has handed out a share, so a box is asked two questions a pass and the memo could only hold the last. Holding both made a scroll cost 3.0 ms in landscape against 11.1.

  It is unsound. Everything a box holds is worked out during that box's own layout, so answering an older question hands back the right size while the boxes below it still hold what some other question produced. A box 101 wide, holding a plain box, holding one string: laid out at a few sizes and back, the string keeps the 40 points it would have measured on its own instead of stretching to 101. Three lines of tree.

  Found by property: forty trees of random shape, each laid out at five sizes, compared against a copy of the same tree that had never been laid out at all. The memo the engine shipped with passes that. Mine failed it 18 times, and my first two attempts to blame the old code were both invalid — the experiment checked one slot while writes still alternated between two.

  A relaxation that is sound — a leaf may answer either question, since what it measured is the whole of its answer — buys nothing measurable, so it is not there either. The layout is back to what it was, and `gui/tests/layout_test.lua` now holds the property, which is the lasting part of this.

- [x] **I8. A scroll event costs 4.7 ms in portrait, 10.5 ms in landscape and the whole frame budget in a split view, and there is roughly an order of magnitude of waste in it.** Counted on the gallery's long list, twenty scroll commits in landscape: **104 boxes in the tree, 3,214 layouts per commit** — thirty-one per box — and the busiest boxes are worked out **a hundred times each in one commit**. Across those commits each was asked only a dozen distinct questions, so most of that work is a question already answered.

  Three memos were written before the shape of the problem was clear, and all three were withdrawn. Each failed the same way and the failure named the cause: a box that answers from memory is never laid out, and a layout leaves more behind than a size. What a caller reads afterwards is `box.pass`, which says whether a frame has to be sent, and the state of everything below the box.

  What ships is two memos, split along exactly that line.

  A leaf keeps its last eight answers and any of them may be given again, since a leaf holds nothing below it. Answering one still runs `record`, so the box is left as a real layout would have left it, `pass` included. Worth about 13% on its own.

  A container keeps its last eight answers too, but hands one back **only to the pass that is asking how large it is**. Sizing a container asks every child its size, shares out what is left and then lays each child out for the share it was given, so the asking never decides where anything below the child sits and the layout that follows it is what puts the subtree in agreement. An answer given there therefore touches nothing but the size, leaves `laid` and `pass` alone, and cannot survive the layout that follows. This is the one that mattered: a subtree was being walked twice per level, so a tree cost what it held raised to its own depth.

  What a box remembers also has to be thrown away, and forgetting that was the fourth failure. A box is rebuilt with an empty memo when it changes, but a box **above** one that changed is not rebuilt, and it was keeping answers taken before the change — a row staying the width of the label it used to hold. `build` already marks those boxes as no longer laid out, and it clears their remembered answers in the same place now, since both are the same thing. Two hundred random trees with one leaf grown: eighty-nine of them kept a stale size before, none after.

  Measured on the gallery's long list, sixty scroll commits over 122 nodes: **2,615 real layouts per commit falls to 773**, and a scroll event costs

  | | before | after |
  |---|---|---|
  | phone, portrait | 4.26–4.54 ms | 3.00–3.13 ms |
  | phone, landscape | 9.23–9.34 ms | 3.61–4.10 ms |
  | split view, 1024×768 | 14.64–15.01 ms | 5.60–6.04 ms |

  Three interleaved rounds, since a single pair of runs on a warm machine says less than it looks like it does. The split view was spending nine tenths of a 60 Hz frame in the layout before UIKit had drawn anything, which is what a person feels as a list that will not keep up with a finger. It is a third of that budget now.

  Soundness is what the first three attempts lacked and what the fourth got wrong in a new way, so it is held by two property tests rather than by an argument. `gui/tests/layout_test.lua` lays sixty random trees out at ten sizes that come back around and compares every frame against a copy that has never been laid out at all, some of those boxes scrolling, since a box that scrolls asks its children something no other box asks. Run outside the suite over eighteen thousand trees at six seeds, every frame matched. The second lays a tree out, grows one leaf and lays it out again against a tree built with that leaf already grown, which is the shape a screen actually has: it holds still and its contents change. A hand-written version of that case was written first and passed against the defect, because the row it measured was being stretched by its parent and so answered the container's width rather than its own — the random trees are there because a case chosen by hand tests what its author already thought of.

## J. What a round on a real iPhone found

Eight defects, every one of them from holding the device rather than from reading the code or looking at a screenshot. Four are things a still image cannot show at all — an animation, a navigation, a mode change, a file chooser — which is the reason this section exists. Closing them found three more, each recorded beside the item that led to it: every icon re-sending its drawing on every commit, an arrival drawn before the node had a frame, and two tests in the suite pinning a defect as if it were the contract.

- [x] **J1. The file and image picker chooses nothing, on any platform.** `gui.FilePicker` declares `props = { "title" }` and `events = {}`, so there is no event a chosen file could ever be reported through — the component cannot work, by construction, whatever the renderers do. And they do nothing: iOS maps `filepicker` to `VarnChooserButton`, which is the `UIMenu` dropdown that `Picker` uses, so it opens a menu of options it does not have. Android maps it to a bare `Button` with no listener. Only the web builds a real `<input type="file">`, and nothing reads what it produces. It declares `kind`, `accept`, `multiple` and `maxBytes` now, and reports `onPick` with an array of `{ name, size, type, bytes }`. Behind it: `PHPickerViewController` for pictures and `UIDocumentPickerViewController` for everything else on iOS, `ACTION_OPEN_DOCUMENT` on Android, the file input on the web.

  Two decisions worth writing down. **The bytes cross as base64 rather than a path**, because the wasm build exports no filesystem to its host, so a path the engine could read is not something the browser can produce — and one renderer answering differently is the disagreement this whole review is about. **Nothing is written to disk**, because where a chosen file belongs is the application's to decide and inventing a cache for it would be a policy the framework has no business holding. `maxBytes` is there because a video read whole is a string no device should be asked to build: anything over it arrives named and measured but unread, which is a case a reader can be told about.

  On Android the chooser is not opened by the renderer. An activity's result belongs to the activity that started it, and a renderer holding one leaks it on a rotation, so the request goes up through `VarnGUIHost.onChoose` and comes back through `chose`, exactly the way the back press already does.

- [x] **J2. The navigation title is not centred, it is centred in what is left over.** The bar is a flat row of back button, title and actions, and the title cell is `grow = 1` between them, so its centre is the centre of the gap rather than the centre of the bar. With a back button reading `Varn GUI` and no actions, the title sits visibly right of centre — which is what the screenshot shows. Apple centres the title on the bar and lets the leading item give way first, truncating the back label to its chevron before the title loses a character. The bar is three cells now, the leading and trailing ones each `grow = 1, basis = 0` so they claim the same width, and the trailing one is there holding nothing precisely so that they can. `gui/tests/chrome_test.lua` measures the title's middle against the bar's for three lengths of back label and for a bar carrying an action: it is 161 of 195 without the fix and within a point of centre with it.

- [x] **J3. Switching from dark to light left white content on a white bar.** `barContent` is whatever the tree hardcoded — the sample says `light` and never changes it — so after the appearance switched to light the status bar was still drawing light glyphs onto a bar that had turned white. Nothing was readable. The answer turned out to be that a screen should say nothing at all. Every platform already draws its own bars from the appearance — `.default` on iOS means exactly that — so a tree that names nothing follows light and dark for free, and naming one pins it for both. The sample says nothing now, `barContent` is documented as the override it is, and the gallery is guarded by a test that fails if anything pins it again.

  The iOS side also kept `VarnSystemBars.wanted` in a global static that no unmount cleared, so a screen that had gone still decided what was drawn over the one that replaced it. The request belongs to a `VarnSafeAreaView` now and is given up when that view is released, which survives the renderer moving a view between parents in a way that giving it up on leaving a superview would not.

- [x] **J4. The carousel's dots are only on the first slide.** `Dots` is appended to the carousel's own children, which are the scrolling content, so the indicator scrolls away with page one and every later page has none. The dots are a sibling over the surface now, so a carousel is a box holding the scrolling surface and the indicator rather than the surface alone. Two more things were wrong and are fixed with it: it drew one dot per entry with no cap, so forty pages drew forty dots wider than the phone, and it is a window of at most seven that travels with the page being read. The note about the safe area was wrong — the dots sit inside the carousel's own box, not against the bottom of the screen.

- [x] **J5. Every list draws a scrollbar, and on the carousel it ruins it.** iOS sets `showsVerticalScrollIndicator` **and** `showsHorizontalScrollIndicator` from one prop regardless of which way the surface actually scrolls, so a vertical list shows a horizontal bar it has no use for. Android already reads the axis and iOS does not. A paged carousel should never show one at all — it says where it is with its dots. On the web `scrollbarWidth` was the only thing set, which Safari ignores, so `showsIndicator = false` did nothing there.

  iOS reads the axis now, and because the axis and the indicator arrive in no order both are held on the view and the pair is worked out again whenever either lands. A carousel defaults to drawing none, since it says where it is with its dots. The web marks the element and a rule in the sheet takes the bar away on `::-webkit-scrollbar` as well as through `scrollbar-width`, so both engines obey.

- [x] **J6. The table's sort order is a text character glued to the title.** `column.title .. " ⌃"`, inside a `numberOfLines = 1` Text, so the mark is the first thing a long column title truncates away, and the glyph is whatever the platform's font has for U+2303 — a different shape and a different size on each of the three. It is a drawn `chevron-up` or `chevron-down` beside the title now, so the title truncates without taking the mark with it. The accordion had the same defect and the same fix, and so did the two chevrons in the sample's own rows.

  Closing it surfaced a defect of its own: an icon's `commands` were compared by identity, so every icon on screen re-sent its whole drawing on every commit. The index grew twenty chevrons and started sending thirteen operations for a render that changed nothing. `commands`, `spans`, `options` and `segments` are compared by value now, the way a style already was.

- [x] **J7. A modal arrives with no animation and leaves by dragging the whole screen down.** It appears in one frame, and on dismissal the scrim goes down with the panel, so the background is uncovered from the top while the overlay is still on its way out. The cause is that the scrim and the panel are one node inside one `Presence`, animated by one transition: `slideUp` moves everything it holds, the scrim included, and moves it forty points rather than off the screen. They are two different moves — a scrim fades, a panel travels the whole of its own height — and they are two now: every presented component is a fading ground holding a travelling panel, and `Presence` honours the style it is given so the panel is the node that moves rather than a screen-sized sheet of glass with the panel somewhere inside it.

  A travel of a panel's own height cannot be written in the tree, since only the layout knows what the panel turned out to be, so `translateX` and `translateY` take a percentage as well as a number and every renderer reads it against the node it is moving. That exposed the cause of the other half: the arrival was drawn when the node was **created**, before it was ever given a frame, so a percentage resolved to nothing and there was no geometry to animate from. It waits for the frame now, on iOS and Android both.

  The action sheet lost its two hardcoded offsets with this — its choices and its way out are one panel stacked from the bottom edge rather than two absolutely placed boxes that each had to know how tall the other was.

- [x] **J8. Every screen is rebuilt when it is returned to, so nothing survives a navigation.** `NavigationStack` renders `screens[index]` and nothing else, keyed by the screen, so pushing unmounts everything underneath and popping mounts a new instance of it. Every `setState`, every scroll offset a list is holding, and every half-typed field is gone on the way back. UIKit keeps the whole stack alive and shows the top of it, and that is what it does now: every screen up to the index is rendered, the top one in the flow and the rest exactly where they were, covered and taking no touches. A screen that is still there is also what a push has to slide over.

  Two tests in the suite were pinning the old behaviour — one asserting the screen beneath must not be built, one that the index gives up the screen — and both were pinning the defect. They assert the new contract now, and the test that matters is a new one: type into a field, push a screen over it, come back, and the field still holds what was typed.

  It costs what keeping the stack alive costs. A scroll event on the gallery's long list goes from 5.7 ms to 6.5 ms in a split view, which is the covered screen being walked, and is still well under half of what it was before I8.

## K. What the second round on the device found

Four more, and two of them were mine — introduced by J8 and J2 in the round above. A covered screen showing through is the clearest lesson in the whole review: a change that is right in principle is not finished until it has been held.

- [x] **K1. A screen pushed over another one let it through, so three screens were legible at once.** J8 kept every screen in the stack alive and left them visible, on the reasoning that a screen is opaque and that a push has to slide over something. Neither holds. A screen is not required to paint a background — the shop's product page does not — so the grid underneath drew its own rows through the product's price, and pushing again put the checkout over the bag over the grid. A covered screen is held rather than shown now: it keeps its place, its state and its scroll offset, and it is not drawn and takes no touches. What a reader sees is the top screen and nothing else.

- [x] **K2. The grid drew its columns edge to edge.** `spacing` went into the row height and nowhere else, so a two column grid gave each column exactly half the width and the halves touched. A share worked out with the gaps taken off first is a length and a percentage at once, which a style cannot say, so each column keeps its share and holds its content half a gap in from each side it has a neighbour on — which is a whole gap between two of them and the grid's own padding at the outer edges.

- [x] **K3. Three controls were drawn with their padding twice.** A badge, a chip and a tooltip each declared it once as what the type is naturally worth and again in the style the renderer draws it with, and the engine added both. A badge showing a single digit came out 32 by 24 for a pill that is 20 by 20, hanging off whatever it was counting and covering the thing beside it. A chip reading `Tag` was a hundred points wide.

  The style is the single source, since it is what the renderer insets the text by, and `natural.padding` is gone from all three. Two defects fell out of fixing it. `natural.sizeOf` returned nothing at all for a declaration carrying only a minimum, so a chip lost the 44 it is never shorter than the moment its padding was taken out. And a natural minimum was applied to the **text** rather than to the box, which is the padding over again — a badge's `minWidth = 20` means the pill is twenty across, not that the digit inside it is.

- [x] **K4. Any rightward swipe anywhere closed the screen, and it closed before the finger was lifted.** The back gesture was a `UISwipeGestureRecognizer` over the whole surface with `direction = .right`. It took a drag on a checkbox, a slider or a carousel as a request to leave, and a swipe recogniser fires the moment the movement passes its threshold, so the screen went while the finger was still down. It is a `UIScreenEdgePanGestureRecognizer` on the leading edge now, acted on when the gesture ends, and only when the drag went far enough or fast enough — which is what the system asks of the same gesture.

- [x] **K5. On Android a finger passed straight through into a box that was told to take none.** `pointerEvents = "none"` set `isClickable = false`, which stops the box and nothing inside it, where iOS stops the whole subtree and the browser does too. It only started to matter with K1 — a covered screen is made of exactly this, so the screen underneath would have kept answering the press meant for the one over it. The box refuses to dispatch now, which is what makes a finger pass through rather than be swallowed: the platform carries on to the next sibling, the same as the other two.

## L. What holding it a third time found

Two reports, one cause underneath them, and the cause had been there since long before this review.

- [x] **L1. Nothing arrived. Every overlay, drawer and pushed screen appeared in a single frame, while the way out of them animated correctly.** `reusable` compared a node with the one it replaces on its **type alone**, and a component's own root is compared with nothing else — there is no key lookup above it, the way there is among siblings. So a component that says it is showing something else by changing the key was patched in place rather than replaced. `Presence` works exactly that way: `absent` becomes `present`, and the node it produced was reused, so it was never created, so `enter` was never applied and there was nothing to arrive from. Leaving animated correctly because that is a style applied to a node that already exists. A key is what says two nodes of the same type are different things, and it now counts wherever the node sits.

  A second defect was hiding behind it, and only became reachable once arrivals worked. A node is framed again in the commit after the one that creates it, and the frame re-resolved the transform from the style so that a travel written as a share of the node could follow a change of size. A node arriving carries its travel in `enter`, not in its style, so re-resolving from a style that names none reset it to nothing — wiping the state the arrival was to come from, a frame before it ran. Only a transform the style actually names is written there now.

- [x] **L2. The drawer did not come in from its side.** It was L1: the panel travels the whole of its own width from the edge it is anchored to, and none of that was applied because the node was never created. Both sides are the caller's to choose and the demo shows each of them now.

## M. What a fourth round on the device found

Seven reports, and the first of them uncovered a defect in the core that had been silently wrong for the whole project: state could not be set to false.

- [x] **M1. The drawer opened and would not close.** `setState` was written `self.state[key] = value ~= none and value or nil`. False is the middle of an `and`/`or` and Lua takes the other branch for it, so **every state a screen set to `false` was stored as nothing at all**. It reads as false everywhere except against false itself, which is exactly where it surfaced: a drawer asking `state.drawer ~= false` got nil, answered true, and stayed open. This is the same `x and y or z` defect the layout had twice, in the one place where it reaches every application written on the engine. It is an explicit `if` now.

  The headless renderer had the identical line for a prop arriving in an update, so a control updated to false — a switch turned off, a checkbox unticked, anything made invisible — read back as nil. Every test asking whether a prop is false after an update was weaker than it looked, and the conformance suite runs against that renderer. The three real renderers compare explicitly and were right.

- [x] **M2. The progress screen ends in a box that says nothing.** `Skeleton { lines = 3 }` reserves the height of three lines and the renderers draw one flat rectangle, so it reads as a component left there by mistake rather than as text that has not arrived. A skeleton is lines, so it is one now: a component that stacks a shaded box per line with the last one short, the way the last line of a paragraph is. The box itself stays a host node, the way a badge's pill does.

- [x] **M3. The bar only moves when a button is pressed.** The demo has an `Advance` button, which shows a bar can be set but not what one looks like while something is happening. It fills on its own and starts again at the end, and says the percentage beside it.

  Making it do that found that a runtime could not be taken down at all. A repeating timer holds the engine's loop open, and every test that mounts a demo left it mounted, so the suite stopped terminating. `Runtime:stop` unmounts the tree, which fires every `onUnmount` and so ends every timer a screen had asked for — a host closing a surface had no way to do that, and nothing in the suite had ever needed one.

- [x] **M4. ## N. What the picker screen on a tablet found

- [x] **N1. ## O. What the suite was not catching, and what it cost

This section exists because a reader on a device found four broken things in a row while every test passed. They were right to say the tests were not worth much, and the reason turned out to be structural rather than a matter of writing more of them.

- [x] **O1. A test could report success for work that never ran.** `async.run` schedules a body and returns — everything after an `await` in it runs once the chunk has ended, if it runs at all. Two `async.run` calls in one file is worse: the second is never resumed, so a whole block of it is dead. Both of those were true in this suite.

  `sample_test.lua` and `runtime_test.lua` each had two bodies, so one block of each had never run. `binding_test.lua` and `list_test.lua` printed that they had finished **outside** their body, so every assertion they made after an await was reached after the suite had already been told they passed. The picker round trip written the day before was one of those: it asserted nothing that anybody ever read.

  Three things close it. Each file has one asynchronous body, its `ok` is the last line inside it, and `run.py test` now reads that line back rather than trusting the exit code — a body that dies prints nothing and the test fails. - [x] **O2. The picker wrote where the process was started, which on a phone is nowhere.** The demo made its directory with `fs.mkdtemp("varn-picked")`, and a bare prefix is relative to the working directory. - [x] **O4. Going back is not animated.** A screen arrives and nothing leaves: the stack renders every screen up to the index, so popping one takes it out of the tree with no exit to draw. A push slides in over what it covers and a pop has to slide back off it.

## P. Gestures, and a turn of the phone

- [x] **P1. A swipe was taken as a press, so scrolling past a row opened it.** Every platform tells a press from a swipe by how far the finger travelled, and none of the three renderers was doing it.

  On iOS a `Pressable` is a `UIControl`, and a control fires when a drag ends inside it however far it went — so a swipe across a row the width of the screen opened whatever the row was for. It follows the touch now and gives it up once it has gone further than the system allows a tap. On Android a view only gives up a click when the touch leaves its **bounds**, which a swipe across a wide row never does, so it is held to `scaledTouchSlop` instead. On the web a `click` is raised whenever a pointer goes down and comes up on one element, however far it went between, so how far it went is watched on the surface and a press that travelled is not reported.

  Writing the Android test found that the fix reported the press ending **twice** — once where the finger was given up and again when it was lifted. One release, reported once.

- [x] **P2. A swipe was not a gesture a tree could answer at all.** It is one now: `Pressable` reports `onSwipe` with the direction the finger went, which is what an item does something different for. Four recognisers on iOS, the axis it went furthest along on Android and the web. A press, a hold and a swipe are three things, and the gallery has a screen where each row answers all three differently.

- [x] **P3. Turning the phone lost everything a reader had put into the screen.** The engine keeps state across a resize — it was the tree above it that changed. The gallery rendered a split view where there was room for both and a navigation stack where there was not, which is **two different trees**: a turn of the device crossed between them and every component under either was taken down and built again.

  `SplitView` had the same defect inside it, so even a caller who wrote one tree lost the panes. It renders one shape now — both panes always mounted, keeping their place and their keys, with only their layout changing — so the instances live through the turn. The pane there is no room for is held out of sight and takes no touches, the same way a covered screen in a stack is.

  The gallery is one tree as well. That needed one thing from the framework: a stack at its first screen may still have somewhere to go back to, which is what the detail column of a collapsed split view is. `NavigationStack` takes `onBack` for it, and the platform's own back gesture reaches it through the same call.

And the library holds pictures and films and nothing else, so a voice note was being filed as a picture: a sound goes to the application's own documents, which the Files application shows because the bundle now says it may, and to the audio collection of the store on Android. `gui/tests/sample_test.lua` reads what the demos reach for out of their own source and fails when the host never declared it.

- [x] **AM7. Beside it, `onError` had two branches in one switch and the second — the one wiring the sound, the film and the page — was unreachable, which the compiler had been saying for some time. Both shapes are now answered by the suite rather than by a warning nobody reads: `promises.unwired()` finds a setter nothing calls and `promises.unreachable()` finds a name answered twice.

- [x] **AM8. The keyboard covered the last messages of a conversation.** The composer rose with it and the conversation did not, since a scrolling surface keeps the offset it had when the room it has shrinks. A surface showing the end of what it holds goes on showing it, on all three — and a surface with nothing to scroll is not at its end, which is the half that has to be said: read as one, a list that fits is thrown to the bottom the moment it grows past its box.

- [x] **AM9. A film could not say it was ready or where it had got to.** Both are declared on `Video` and iOS had a property for neither, so a tree drawing its own scrubber over a film had nothing to follow while a sound reported both.

- [x] **AM10. Five controls in the demos answered a finger by doing nothing.** A search that searched nothing, a menu that opened nothing, a field whose text was thrown away as it was typed, a button that was going to change a picture, and a reply that replied. What the data behind a demo is does not matter, and that it is invented least of all: a control that is there to be looked at is a lie about what the framework does. The suite reads every handler in the sample and fails on one with an empty body.

- [x] **AM11. Twenty-four of the icons the engine ships were drawn by nothing.** A name nobody draws is a shape nobody has ever seen come out. The gallery draws the whole set, and the suite holds every name to drawing something and holds the gallery to drawing all of them.

- [x] **AM12. The listening application was a set of tabs, which puts no weight on anything.** It is a path now: categories, the groups inside one, the shows in a group, a show — and the show naming its category and its group as things a reader presses to open them again on top, so the way in has no end. The suite goes round that loop six times, holds sixteen screens, checks that what is playing followed the whole way down, and unwinds every one of them through the way back. A stack is easy to get right two screens deep, and what it costs only shows at twenty.

- [x] **AM13. The public table carried what was never meant to be on it.** Every export of a component family was copied onto `gui`, and a family also carries the helpers its own components and its siblings are built from, so `gui.over`, `gui.scrim`, `gui.moments` and the three travels stood there beside the components — undocumented, untested, and enough to make a component named after one of them later fail as a name two families define. `gui.X` is a component now. Fourteen module exports that nothing outside their own file ever read are local.

- [x] **AM14. There was nowhere to keep what an application must find again.** `gui.preferences` is `set`, `get`, `remove`, `clear` and `names`, carrying a string, a number, a boolean or a table and answering when the keystore answers. It is the keychain on iOS, an AES key generated inside the Android keystore sealing a private file, and on a page a non-extractable key in IndexedDB encrypting the values — which the documentation states plainly is origin isolation and a key the page cannot export rather than a secure element.

- [x] **AM15. Three public modules had no page, and two were public by accident.** `gui.X` is API, and `Router` stood in the reference table with nothing anywhere saying how a screen under one goes somewhere: routing, contexts and observables are written down now. `gui.element` and `gui.routing` were reachable as `gui.X` and nothing ever reached them that way, so they are required by path like the rest of the framework's own parts. `gui/tests/components_test.lua` holds every module on the table to being mentioned by a page.

- [x] **AM16. The browser suite was a gate nobody could trust.** It waited on the clock rather than on the thing: two seconds is plenty for a recording to be written on an idle laptop and not enough while the same machine is building an application for a phone, which is the same reasoning `gui/tests/waiting.lua` already carries on the Lua side. Six waits that were waiting for a result now wait for the result — the note, the picture, the film, the look reaching the preview, the screen saying it was kept, and the file the browser writes after saying so. What is left is the two that are the thing being measured, which is a recording running for as long as it was told to.

- [x] **AM17. A measurement was remembered under a name that left out half of what it depends on.** The letter spacing, the line height and the slant each change how much room a string needs and none of them was in the key, so the same string at a different spacing answered the measurement taken for the other — which `CLAUDE.md` had been asserting was already the case. The room the string has is taken to whole points as well, since a layout works its bounds out of shares and arrives at a different fraction on every pass. Beside it, the cache was held at five hundred entries where one screen asks close to five hundred questions, so it filled on the way into a screen, gave up the older half, and measured the whole of it again on the way back. A cache smaller than one screen answers nothing.

## AN. A nineteenth sweep, at the contract a fourth renderer would be written from

- [x] **AN1. The porting contract was two functions short of what a host is actually asked for.** Every host passes the engine a piece of Lua to launch with, and it calls back into itself from inside that string: `host.gui_problem` is how all three report a start that failed or a commit that raised, and `host.gui_framework` is how a host that shares no filesystem with the engine hands the framework over as bytes. Neither is called from anywhere under `gui/`, so neither was in the document — somebody writing a fourth renderer to it had an application that dies with nothing said and, if its engine has no filesystem of theirs, one that never starts at all. Both are written down, and `gui/tests/host_test.lua` reads the three hosts as well as the framework, which is what found the second one after the first was added by hand.

- [x] **AN2. The page went on reporting into an engine that had stopped answering.** `WebHost.send` pushed onto a queue only the pump drains, and the pump does not run once the host has stopped: every resize, pointer and keyboard report after that piled up behind it and nothing ever came back for them. A stopped host takes nothing.

- [x] **AN3. Two custom properties the sheet read and nothing ever set.** `--varn-activity-track` and `--varn-chosen-color` were written by none of the three renderers, so what a spinner's track and a chosen control actually drew was the literal beside them every time. They are that literal now, which is what they always were.

- [x] **AN4. The demos are built after the shape of applications a reader knows, and nothing held them to naming none of them.** Copying a shape is what a demo is for and saying whose it is belongs to nobody here. `gui/tests/sample_test.lua` reads the sample and every page under `docs/` and fails on a product name in either, checked against a planted one. A word that is also ordinary English is deliberately not on the list — a show in the listening application is called Signal and Noise, and the browser host aborts its listeners with one.

- [x] **AN5. The Lua suite waited on the clock in four places, and one of them failed while a phone was being built.** The browser suite had been fixed for exactly this and the same reasoning was never carried back to the side that already had the helper for it: a demo was given twenty milliseconds to write a chosen picture to disk, a sheet six hundred to travel out, a moment four hundred to be announced twice, and a carousel sixty to come round to its first page. Each waits for the thing now. What is left sleeping is the three cases where the sleep is the proof — a pulse on a tab nobody is looking at, a screen that has been taken down, and a carousel told it may not loop — since a non-event cannot be waited for. A carousel that waits for the wrap also stops passing vacuously, which is what a starved loop had been doing to the half of that pair that expects nothing.

- [x] **AN6. Three browser cases failed together, and what failed was that the suite had been leaking browsers all along.** The three that fail are exactly the three that launch a browser, and they fail together because none of them could start one. A browser is a tree of processes rather than one — a launcher and seven helpers on this machine — and closing it signalled only the process that had been spawned, so every run left the helpers of all three holding the machine. Seventy-eight of them were running by the time this was looked at, from eleven runs, and none of their profiles had been removed either, since the close was still waiting on an exit that was never coming. A few runs of the suite and the next browser could not start inside the time it is given, which the suite then reported as three defects in the renderer. Each browser is launched into a process group of its own and the group is what is signalled, one that will not go within five seconds is ended rather than waited for, and every browser this process launched and has not closed is ended when the process itself ends, so a run that is interrupted leaks nothing either. A failed start closes what it started. `renderers/web/tests/browser.test.js` holds a closed browser to leaving nothing of itself running. The time a browser is given to start went from twenty seconds to forty-five on the way past, since a machine driving a simulator is slower than an idle one, but that was never the defect — it was the leak feeding on itself.

- [x] **AN7. The gallery's own cases waited on the clock in three places, and one of them failed.** Pressing the cover on a tab bar opens the system's picture library, and what proves it opened is that the gallery is no longer what is on screen — asked three seconds later by pressing the gallery's own element, which raises rather than answering no once that element has left the snapshot entirely. It waits for the screen to be covered or gone, and for the gallery to come back after. Beside it, a conversation was given three seconds to be answered: it waits for the answer, and for any of the three the other side may give, since which one comes back depends on how much has been said and a bubble may be read through the row that carries it.

## AO. Frames drawn from artwork, and what building one found

- [x] **AO1. There was no way to build an interface out of artwork.** A picture stretched to fill a box has its corners pulled out of shape, so a panel with an ornament on it could only ever be drawn at the one size it was authored at. `gui.NineSlice` cuts a picture into nine: the four corners are drawn at their own size, each edge stretches along one axis only, and the middle stretches both ways. It holds what is written inside it the way a view does and it reports a press, which is what makes the same component a window, a dialogue and a button. The browser draws it as a border image, iOS from a layer told where the middle of its contents is, and Android as nine pieces, since the platform's own nine-patch reads its cuts out of marker pixels compiled into the file rather than taking them as numbers.

- [x] **AO2. A picture a frame is cut from is the one exception to the density variant.** The cuts are four numbers of pixels and they point at the file the caller named. Handing a renderer the `@2x` twice the size would cut that picture at the same four numbers and draw every corner at half the width it was authored at, so a nine-slice source is resolved at the plain name. That is a third kind of source beside the ones a density variant suits and the ones a platform player streams, and it is named as one in the runtime rather than left implicit. A frame that has to be crisper is shipped larger and drawn smaller.

- [x] **AO3. A frame is painted over the box and never inside it.** Children arrive at frames the engine already worked out, so a border with a width of its own shifts every one of them inward by its own thickness — and the browser is the only one of the three where that is even possible, which is precisely what makes it a trap. The browser draws the frame with `border-image-width` over a border of nothing, so the same tree comes out laid out identically in a browser and on a phone.

- [x] **AO4. A shorthand three renderers each read for themselves is three chances to read it differently.** `slice = 16` and `slice = { top = 16, … }` are the same thing, so a declaration may now `normalise` its props before it validates them and the four cuts cross as four numbers however they were written. Nothing downstream carries a second reading of it.

- [x] **AO5. A frame cannot be narrower than the two corners it is cut at.** Narrower than that they overlap and what comes out is not the picture. That minimum is not fixed for the type but worked out from the cuts the node was given, so `gui/layout/natural.lua` takes a minimum as a function of the props the way it already took a size. A picture cut wider than itself has no middle left to stretch and is drawn whole instead, on all three.

- [x] **AO6. The artwork is drawn rather than found.** `tools/draw-frames.py` draws the five pictures the demo is built from — a panel with a bracket at every corner, the same panel with a bar across its top, and three chamfered buttons — so the next one is drawn rather than traced. They are nine-sliceable by construction: the corners carry the ornament and the edges carry only what may be stretched along them.

- [x] **AO7. The screen found two things no test had.** A component reads its children through `self.children`, and the demo was reading `self.props`, so every window drew its frame perfectly and held nothing at all. And a plate in a wrapping row was given a share of the row rather than the width of its label, so a longer label wrapped inside its own button. Both are exactly what the rule about looking at a screen exists for: the tree was the right shape either way.


- [x] **AO12b. Closing the browser properly stopped the suite from ever finishing, and the reason is a corpse.** A child that has gone and has not been collected stays in the process table, and its group still answers — so a close that asked "is the group still there?" was answered yes for ever. It spent five seconds asking, five more after a kill, raised inside the case's own teardown, and left the run unable to finish. Waiting on the child's exit is what makes node collect it, so the order is: signal the group, wait for the one that was spawned to exit, and only then ask after the helpers. Measured against a guard rather than by watching. The first run took thirty-six seconds and the second and third had to be killed at a hundred and fifty. Three runs now take thirty-seven, thirty-six and thirty-five, and the whole suite leaves nothing running.

- [x] **AO12c. The same fix was written into the file twice and the second time it landed outside the class.** A replacement whose anchor was not found replaces nothing and prepends instead, so sixty-seven lines of methods were pasted above the imports and the module stopped parsing altogether. It cost a run to notice and a minute to undo, and it is the argument for the check being a build step rather than a habit: `node --check` said so immediately and is what the next edit ran first.

- [x] **AO11. The leak was closed twice, and the second half of it is what had gone on failing.** Signalling the whole group rather than its leader was right and was not enough: `close()` waited for the leader's `exit` and returned there, while the seven helpers behind it were still going. So a run still left browsers behind, fewer and for less time, and the three cases that launch one still failed together when enough of them piled up — which is the failure that was recorded here as unexplained. The case written to hold the first fix is what caught it, by failing intermittently itself: it asks whether anything of the group is still running the moment `close()` returns, and sometimes something was. A close now waits for the group to be gone rather than for its leader to exit, escalates to a kill if it will not go, and raises rather than returning quietly if even that fails.
- [x] **AO8. The capability names were written down in three places and held together by nothing.** They live in the contract and each native suite carries a copy to hold its own renderer against, so adding one to the contract and to the three renderers still left two lists behind — and what that looks like is a suite failing on a capability that is perfectly correct, which is exactly how it was found. `promises.uncontracted()` reads the contract and both copies and the suite holds them at agreement, checked against a name taken back out of one of them.

- [x] **AO9. Two renderers carried a policy the engine already owns.** Each defended itself against a `sliceScale` of nothing by quietly substituting one, and the engine refuses that value where it is written. A renderer owns no policy: a second guard against something the contract forbids hides a defect rather than catching one, and it is two places to change when the rule changes.

- [x] **AO10. The Lua suite's patience was four seconds and the work it waits on is real.** A file read through the pool, a picture fetched, a recording written — four is plenty on an idle laptop and not enough on one that is also building an application for a phone, which is the third time this session that the same reasoning has had to be applied somewhere it had not been. It is ten now, which costs nothing when the thing happens at once.

- [x] **AO12. The artwork and the cuts it is drawn for lived in two files and agreed by luck.** The four numbers are written in the screen that draws the frame and again in the script that draws the picture, because the script has to know them to check its own work. They had already drifted: the script declared the titled window cut at forty-six on all four edges and the screen cuts it forty-six along the top and twenty-eight elsewhere, which made the script's own check weaker than the thing it was checking. Both carry the same four numbers now and `gui/tests/nineslice_test.lua` holds them together, proven by putting the drift back.

- [x] **AO13. The drawing script refuses to write artwork its cuts would smear.** An edge strip is stretched along one axis, so every row of a side edge has to be the same row of pixels and every column of a top or bottom edge the same column. Anything sloped, tapered or rounded crossing a cut line is drawn once in the corner and pulled out of shape in the strip beside it — and looking at the stretched output, which is the obvious check, does not see it, because the output is compared with itself. Reading the pixels does. The five pictures this repository ships pass it with nothing to report.

## AQ. A review of what an application is told and when

- [x] **AQ1. What the engine needs is not the screen's to declare.** A renderer binds an event when a handler for it crosses the bridge, so anything the engine itself listens for is reported only when the application happens to want it too. The engine lifts a focused field clear of the keyboard and learns which field that is from `onFocus` — and no screen has a reason to declare one, so on every screen with a field, on all three platforms, the keyboard came up over the field that had just been pressed. The suite's own keyboard case had been declaring the missing handler, which is exactly why it never saw it. A field reports focus and blur because the engine needs it, and the same reasoning gives a surface its offset while something under it is watching.

- [x] **AQ2. Nothing anywhere knew the application had gone away.** Not one of the three hosts handled any of it: not `didEnterBackground` or `willResignActive`, not `onPause` or `onStop`, not `visibilitychange` or `pagehide`. An application built on this could not save a draft before being suspended, could not let go of a camera while away, could not stop a timer that would run a battery down, and was never told it had come back. `gui.lifecycle` carries one of three states, since active, inactive and background mean three different things and an application that treats them as one either saves far too often or is ended with the reader's work in it. `gui_surface` answers the state at start, so one launched out of sight is not told it is in front.

- [x] **AQ3. The half that makes the three agree.** A suspended application runs nothing, a paused activity goes on running, and a hidden tab is throttled without stopping, so the same timer fired three ways. Anything a component asked for through `self:after` or `self:every` now waits while the application is away and happens on the way back. None of that is the application's to write three times.

- [x] **AQ4. A moment queued for a pump that is not coming is a screen never told.** The frames stop when the window goes — `requestAnimationFrame` does not run for a hidden page and a display link does not tick for a suspended application — so a lifecycle event handed over in the ordinary way would sit in the queue for ever. All three hosts hand it over and pump in the same breath.

- [x] **AQ5. Running low on memory is its own moment and nothing answered it.** The engine held four thousand measurements and a store of picture bytes and gave neither back. `gui.memory` gives up what can be worked out again — a measurement is taken afresh the next time a string is laid out and a picture's bytes are built afresh the next time one is drawn — and nothing a screen put anywhere.

- [x] **AQ6. Appearing is not being seen, and there was no way to say the second.** A component is told when its screen is shown and a list tells a caller which entries entered its window, and between them an ordinary box scrolled into sight said nothing at all. `onEnterView` and `onExitView` are the engine's own arithmetic over the frames it laid out and the offsets it is told, so a browser's observer and two hand-written implementations beside it do not have to agree by luck. The rectangle is carried up through every surface between the box and the screen and cut by each in turn, since a box sitting perfectly inside a list that is itself scrolled away is not visible — and measuring against the screen alone answers that it is, which is the whole difficulty. The first version of that case passed without the clipping, which meant it was testing nothing, and it was rewritten to turn on the inner surface alone.

- [x] **AQ7. An application could not say whether it owned the whole screen.** `SafeArea` says three things about the system's bars rather than one: which edges the tree keeps clear of, which bars the reader still sees, and what the marks in them are drawn in. Hiding one gives its room back, so the insets change with it and a screen stays correct across the change. What a platform cannot do it says through a capability: iOS takes the status bar away and will only let the home indicator fade, and a browser has no bars at all and full screen instead, which it grants only inside a gesture.

- [x] **AQ8. A field could not be as tall as what was in it.** `TextArea` had a number of rows and nothing else, so a composer or a note — the two things it is most used for — could not be built. `grows` makes the height a measurement of the text, which changes on every keystroke and is answered by the engine's own measuring rather than by a renderer. The gallery's **Writing** screen shows it beside a field of fixed rows and beside an editor over styled runs.

- [x] **AQ9. What a rich editor is, said plainly rather than implied.** The framework draws styled runs and the document they are drawn from is the application's. A caret **inside** those runs — a selection spanning two of them, a mark applied to part of one — is not there and is not pretended to be. Owning that means owning a text engine, which is a decision rather than an omission, and building the demo is what made the line visible.

- [x] **AQ11. A case failed once and the name was thrown away by the command that ran it, and that command is in the repository.** The run was piped through `grep -E "error:…" | tail -3`, and the three lines a `tail -3` keeps are the two summaries and `** TEST FAILED **` — so the line naming the case, which the grep had caught, was discarded one step later. It was not a case failing silently in its own teardown, which is what I guessed before looking properly. Worse than the one-off: the same shape is in `.github/workflows/check.yml`, where both iOS steps filtered the output down to `Executed …` and `** TEST SUCCEEDED/FAILED **` and never included `error:` at all — so a failure on CI would have been just as nameless, every time, for anybody. Both steps carry it now. Eleven runs of the suite since, with the whole log kept, are clean at thirty-four tests with one skipped. What was left of this was a defect in how the suite is read rather than in the suite, and that defect is closed where it lives.

- [x] **AQ10. A stand-in that is missing what the code uses is a suite agreeing with itself.** The page's document had no `addEventListener` at all, so the host that watches it could not start under test — and when it was given one, it kept a single handler per event, which quietly dropped one of the two the host registers for a page being hidden. A document that holds one listener is not a document.

- [x] **AQ12. A run of text inherited everything on a page and nothing on a phone.** A browser takes the colour and the size from the element the runs sit in. A phone builds each run's attributes from that run's own style alone, so a run that named a weight and nothing else came out in the paragraph's colour on one platform and in black on the other — which on a dark screen is a sentence with a hole in it, and nothing about the tree says so. The engine lays each run over the paragraph before it crosses, once, so the three cannot disagree about it.

- [x] **AQ13. A field over several lines showed its placeholder everywhere except on a phone.** A one-line field is a `UITextField` and carries one. A field over several lines is a `UITextView`, which the platform gives no placeholder at all, so the same tree showed the words on a page and an empty box on a phone. It is drawn now, in the platform's own muted colour, and goes as soon as there is anything to read. Both of these were found by looking at a screenshot of the screen rather than by any case, since the tree is the same either way — the field has the right type, the right size and the right prop.

## AR. A twentieth sweep, at what a day on the phone found and at what the platforms offer

A round reported from the phone: a scrubber that seeked once and then stopped following the sound, a first screen that arrived with an animation it had no reason to have, a bar whose contents read as resting on a line, a large title cut by the bar's own rule, a field screen thrown up by the keyboard and left there, applications that did not read as applications, and a rich editor that was two boxes. Beside it, three things asked for — a bar that takes items, artwork per state on a frame, and forms — and one question: whether what an application is told here is what the platforms themselves tell one.

- [x] **AR1. Seeking was a command written as a state, and it went wrong in both directions.** `gui.Audio` declared `position`, so the tree wrote the moment a scrubber was dragged to. A prop is sent only when it differs from the last one, so dragging twice to the same moment was silent the second time. And clearing it when the drag ended removed the prop, which crosses as `"__varn_removed__"` — read through `VarnValue.number(value) ?? 0` on iOS and `(value as? Number)?.toDouble() ?: 0.0` on Android, which is nought, so letting go of the scrubber seeked the sound back to the beginning on both phones. Seeking is the `seek` action now, on `Audio` and on `Video`, asked through a ref beside `play` and `pause`, and a `seek` asked of anything that is not a sound or a film is refused by name on all three. Held on four platforms, each checked against the old code.

- [x] **AR2. An action was a promise nothing held anybody to.** A prop listed in the reference is one `promises_test` holds to being honoured by all three renderers, and an action — `scrollTo`, `focus`, `capturePhoto` — was written in no declaration and checked by nothing. Actions are declared beside the props now, the reference carries a column for them, and `promises.unanswered()` fails when one is performed by fewer than three renderers. Proven against a declared action nobody performs.

- [x] **AR3. The first screen of a stack arrived as though it had come from somewhere.** `NavigationStack` gave `enter` to whatever was on top, including the very first commit, so opening the application slid the menu in from the side of the glass. A screen arrives when it was not there the last time the stack drew, which is what a push is — and deciding it instead from whether the stack had ever drawn put an `enter` on the next unrelated commit for a screen that had not moved, which is two operations over the bridge for nothing and is what the performance budget caught. `transition` chooses the move, `"none"` included, a screen may carry its own, and `animatesFirstScreen` is there for a caller who wants the opening one to arrive.

- [x] **AR4. The bar did not own the top of the screen, and it showed at the join.** The application drew inside the safe area, so the bar began below the clock and the strip above it was a painted rectangle belonging to nothing: a bar with a colour of its own ended in a hard edge under the status bar, and a screen travelling in a push travelled only the part below it. Whether a bar should take that strip cannot be worked out from a prop, since it depends on what stands above the bar rather than on what the bar was told — so a safe area now provides the insets it did not take to everything under it, and the same bar adds the strip on a screen drawn edge to edge and adds nothing inside a safe area. ## AS. A twenty-first sweep, at what a full read of the project found

No report from a phone this time. The whole tree was read for defects — what can kill a running application, what is left over, what two things can do to each other at once, and what one platform does that the other two do not. Eleven things came out of it, and six things that looked wrong and are not are written down at the end so that the next read does not spend the time again.

- [x] **AS1. A sound that the tree moved never reported where it was again.** A node moves when its place among its siblings changes, which a list that reorders, a screen that is pushed and a child that appears above another all are, and the Android renderer performs a move as `removeView` followed by `addView` — so a move is a detach and an attach. `VarnAudioView` posted the ticker that reports its position in its initialiser and removed it in `onDetachedFromWindow`, and nothing anywhere posted it again. The first time anything appeared above a playing sound the position stopped arriving: the sound played on, the clock beside it stopped counting and the scrubber stayed where it was. It is the defect AR1 closed, on the same control, reached by a different route. The ticker belongs to the sound rather than to the window now, and `MediaTest` moves a playing sound and reads a later position back.

- [x] **AS2. A recording in progress was thrown away when its node moved.** `VarnRecorderView.onDetachedFromWindow` called `release()`, which stops the recorder, releases it and drops the file it was writing. `finish()` is the path that answers `onFinish` with that file and how long it ran, and `release()` is not that path, so a move while recording lost the recording, orphaned the file and left the screen waiting for a report that never came. The override is gone: `VarnRenderer.remove` already releases a node the tree has genuinely taken out, and `VarnGUIHost.stop()` reaches the same path through the batch the engine's own unmount produces.

- [x] **AS3. The video and the camera released twice for one detach.** Both draw through a `TextureView`, whose `onSurfaceTextureDestroyed` already releases the player and closes the camera, and both also overrode `onDetachedFromWindow` to do it again. Nothing broke, because the second call lands on a device already let go of, but two paths did one thing and a reader of either file had to find both. The surface's own callback is the one place now. iOS is the shape being matched: `didMoveToWindow` stops the session when the window goes and opens it again when one arrives, so a move there costs a restart rather than a life.

- [x] **AS4. A sound or a video was told it had ended whenever any other one had.** `VarnAudioView` and the video view both observed `AVPlayerItemDidPlayToEndTime` with `object: nil`, and nothing as the object is every item in the process. A screen holding a sound and a video told both of them they had finished when either one had: `onEnd` reached a screen for a node halfway through, and a node with `loop` on seeked back to nought and started playing because something unrelated ran out. Each now matches the notice against its own current item, and a case on each of the two ends one player and reads that the other was not told.

- [x] **AS5. An editor never said where its caret was on Android.** `VarnProps` routes an event by name through a `when`, and `"onSelectionChange"` had two arms — the field's and the editor's. A `when` runs the first arm that matches, so the editor's was unreachable: the row of tools over an editor never lit up for what the caret was inside of, on the platform where nothing said so. The compiler had been printing `Duplicate branch condition in 'when'` on every build. One arm answers for both controls now, `promises.shadowed()` reads that `when` alongside the browser renderer's run of checks, and `WritingTest` is the first case on this platform to drive an editor at all.

- [x] **AS6. A handler was bound after the prop that reports through it.** Props were applied in whatever order the batch happened to carry them, with only what a control is made of pulled to the front. Applying a prop can report before the batch is over — a source that cannot be opened is refused where it is set — and a handler bound afterwards is one whose only word about it went nowhere. A handler goes first now, then what a control is made of, then everything else.

- [x] **AS7. A sound that could not be opened said nothing at all on Android.** `setSource` wrapped `setDataSource` and `prepareAsync` in `runCatching {}` and dropped what came out, so an address that does not resolve, a file that is not there and a format the device cannot play were all silence behind a play button that does nothing. `Audio` declares `onError`, iOS reads it off the item's status and a browser raises `error` on the element. It is reported now, and a case gives a sound a source that cannot be opened.

- [x] **AS8. A sound ignored `rate` on Android.** `VarnProps` applied `rate` to the video and to nothing else, while the `volume` branch immediately above it applied to both. A recording played at one and a half speed played at one. The sound carries a rate like the video does, applied where playing starts since a player only takes a speed while it is running.

- [x] **AS9. Two children of one node under one key lost one of themselves.** A key is what says which child a description means, and `patchChildren` indexes what it holds by key, so two children under one key left the second standing where the first was. Both are drawn on the first commit, which is why it never surfaced where it was written: on the commit after, the first matched nothing, was taken down, and a row a screen had drawn disappeared with nothing anywhere saying why — no failure, no warning, one row fewer. A key that is a table was already refused by name, so the shape of a key was checked and the one thing a key is for was not. It is refused where the children are read now, naming the key and the node, and a case writes one, reads the refusal back, and checks that the same key under two different parents is still two different children, since a key is only ever compared against its own siblings.

- [x] **AS10. What is left over, and the two checks that answer for it.** `MARGIN` in `gui/runtime/init.lua` was a copy left behind when the keyboard moved into a file of its own, three imports were from that same split, a constant in the mail application was a number the bar works out for itself, and a comment block in `runtime_test.lua` had been pasted four times over describing a case it did not sit above. `promises.unread()` answers every name a Lua file declares for itself that its own file never reads, which is what none of Lua, the suite or a reader was going to catch. A set of comments narrating what the code used to be were rewritten as the reason the code has the shape it has, which is what this file is for and a comment is not.

- [x] **AS11. Starting a tree on something that is not a renderer failed somewhere else entirely.** `M.start` checks that the description is an element and that the surface is two numbers, each by name and each with the reason written beside it, and then reached `renderer:showTheme`. A caller who passed the options where the renderer goes was told `attempt to call a nil value (method 'showTheme')` by a line that has nothing to do with what they got wrong. A renderer is the third of the three things the engine cannot work without, and it is named with the other two now.

### Looked at and found sound

- **`a and b or c` where `b` is nought.** Nought is true in Lua, so `natural.sizeOf`, `flex.intrinsic`, the cross size a child is stretched to and the height `inView` measures a surface against are all correct as they stand. The shape is only wrong where the middle can be `false` or `nil`, which is what `CLAUDE.md` says and what the three defects already closed for it were. Every `and`/`or` in the tree was read against that rule and none of the rest can yield either.
- **`table.unpack` with a comma after it.** A trailing separator does not move which field is last, so every `{ ..., table.unpack(t), }` in the tree expands. Checked against the engine rather than assumed.
- **Everything is reached.** Nothing under `gui/` is unreachable from `gui/init.lua`, from `gui/components/families.lua`, from the suite or from the tools, and no renderer carries a private function nothing calls.
- **The browser host lets go of what it takes.** Every global listener it adds carries the abort signal it tears down with, and the resize observer is disconnected in `stop()`.
- **A moved node on iOS and in a browser.** iOS reparents with `addSubview`, and the camera opens itself again from `didMoveToWindow`. A browser takes the element out and puts it back inside one task, and the pause a browser queues for a media element that has left the document asks again when that task runs, by which time the element is back.
- **A window that walks its own offsets.** `gui/collections/window.lua` rebuilds from the first entry a measurement changed, and every path that could ask it for an offset it has never built resets the whole table first, so the arithmetic that adds the entry before it can never reach a nil.

## AT. Controls drawn by the engine, and the theme that says how

A second way of drawing every control: a **control theme** that says what a control is made of, drawn by the engine out of boxes, text and paths rather than handed to the platform. A look says what a control is coloured in, a control theme says what it is built out of, and the control theme reads the look. The point of it is portability — a renderer for a fourth platform then needs a box, a string, a picture, a path, a surface that scrolls and one editable text run, and everything else is drawn the same way on every platform.

- [x] **AT1. A control is one public name and two ways of being drawn.** `gui.Switch` is the platform's own switch under `native` and a drawn one under any other control theme, with nothing about the screen changed. Which of the two is never the screen's to decide, since the whole point is a tree written once. A component that may be handed to the platform declares the host type as `platform`, so its props are held to being honoured by all three renderers exactly as a host node's own are — a component that quietly stopped being a host node would otherwise take the check with it — and `docs/components.md` writes it as `` `switch` or Lua ``.

- [x] **AT2. A control theme is a complete set, checked where it is written.** `gui/controls/theme.lua` carries what one is: an entry per control, each carrying the sizes it is drawn at, a colour role per part per state, how long a change takes and on what curve, and what a finger does to it. One that leaves a control out, names a part no control has, or paints a part in no state at all is refused at `define` rather than drawing nothing on a screen. `extend` writes what changes over another, so Material 3 with square corners is the corners and nothing else.

- [x] **AT3. A colour is a role, which is what keeps the two themes apart.** A control theme never names a colour. The roles a drawn control needs beyond the ones a look already carried — `outline`, `surfaceVariant`, `onSurfaceVariant`, `primaryHover`, `primaryMuted`, `secondaryContainer`, `onSecondaryContainer` and the three disabled forms — are worked out from the ones it does, so a look written before this library drew a control is still a complete palette and one that names any of them is taken at its word.

- [x] **AT4. The control theme is read in one place.** The component that chooses reads it and hands it to the drawn one as a prop. Read in both, both owe a render when it changes, and the drawn one is rendered against a theme that no longer draws it — an index into a table that says `platform` and nothing else. It surfaced the moment a test switched back to the platform's controls.

- [x] **AT5. A drawn control says what it is, what it is doing and what it is at.** A control the platform draws tells a screen reader all of that for itself, and a box drawn to look like one tells it nothing: the drawn set would have been a regression for every reader using VoiceOver or TalkBack. `accessibilityRole`, `accessibilityState` and `accessibilityValue` are universal props now, honoured by all three — traits and the value on iOS, an `AccessibilityNodeInfo` through a delegate held beside the view on Android, and ARIA attributes on the page. The delegate is held in a map keyed by the view rather than in a view tag, since Android refuses any tag key that is not an application resource id and this renderer declares none.

- [x] **AT6. A drawn control is touched through a box at least the size of a finger.** A design publishes the size it draws a control at and every system publishes the smallest target a finger can reach, and they disagree: Material draws a 40dp button and asks for 48. The press is taken through the larger box and the smaller one is drawn inside it. The guideline suite caught every one of them — a stepper key at 40, a rating mark at 28, a button at 40 and a segment at 24 — which is what that check was written for.

- [x] **AT7. A drawn control declares the size it has of its own.** A control the platform draws carries a natural size the layout reads off its declaration. A drawn one is a box the layout knows nothing about, so left to itself it fills the column it was written in, which is a switch as wide as the screen.

- [x] **AT8. Eight controls, four control themes.** Switch, checkbox, radio, button, segmented control, stepper, rating and select are drawn by the engine under `material2`, `material3` and `cupertino`, and handed to the platform under `native`. The select is the one where drawing it is better than not: what the platform draws there is three different controls with three different behaviours, and drawn it is one. Held by `gui/tests/controls_test.lua`, and the gallery draws all four designs on one screen under **Controls** with a chooser that puts the whole application into any of them.

### What this round did not finish

- **A focus ring.** `Pressable` reports pressing, hovering and keys, and nothing reports focus, so a drawn control cannot draw one. It is the whole of keyboard use on the web and on a tablet with a keyboard.
- **The slider, and the drag it needs.** `docs/events.md` lists a continuous drag as deliberately not built, and a drawn slider needs one. `Slider` is still the platform's own under every control theme.
- **The field.** What a control theme draws around a text input — the container, the outline, where the label sits, the helper line — is designed and written down and not yet built. The editable run itself stays the platform's, which is a boundary rather than a gap.
- **The cost.** A drawn control is several nodes where a native one is one, and the performance budget has no case for a screen of them yet.

## AU. The control theme opened, and the ways a person uses a control

Section AT built the control theme and drew eight controls with it. What it left was a fixed menu: ten kinds named in a closed table, a control theme that could recolour a switch and never rebuild one, and drawn controls that answered a finger and nothing else. This round makes it a platform and gives every drawn control the three ways a person has of using one.

- [x] **AU1. A kind of control is registered rather than listed.** `CONTROLS` was a literal, so a control the library did not ship could not be part of a control theme at all and nobody could add one. It is a register now: `gui.controls.kind` declares a kind and the parts it is painted in, the ten that ship declare themselves through the same call, and `gui.control` declares a whole control — it registers its kind, takes the declaration a component takes, is checked and documented like any other, and a control theme may carry an entry for it.

- [x] **AU2. A kind carries the entry it is drawn with, because the alternative breaks every theme already written.** A kind registered after a control theme exists would leave that theme incomplete, and the four the library ships are built the moment it loads — so adding a control would have broken all of them. A kind brings its own default and a theme writes over what it wants to change. The fallback is read where the entry is looked up rather than folded in where the theme is built, which is what makes it reach a theme that was built before the kind existed.

- [x] **AU3. A control theme may replace a drawing, not only recolour it.** An entry may carry `draw`, a component handed the props and the theme. A design that wants a switch with its words inside the track writes one and changes nothing else, and the design it was extended from is untouched.

- [x] **AU4. A control no system draws names no platform node.** A round progress is one of those: what a system draws round is a spinner, which says something is happening rather than how much is done. `ProgressCircle` is its own kind, drawn by the engine under every control theme including `native`, and a theme that tries to hand it to the platform is told by name rather than failing somewhere inside a render.

- [x] **AU5. Focus, which is the whole of using a keyboard.** A key already reached whatever had focus and nothing reported focus, so no drawn control could draw a ring and using one from a keyboard was pressing keys at a screen that never moved. `focusable`, `autoFocus`, `onFocus` and `onBlur` are honoured by all three — the focus engine and the responder chain on iOS, `isFocusable` with a listener on Android, `tabindex` with the two events on the page. Every drawn control is a stop on the way through and paints the state the control themes already carried and nothing could reach.

- [x] **AU6. A focus ring is one thing for a whole design.** It is the same on every control a design draws, so the control theme carries it once rather than as a state on every part of every control. It is a box outside the control rather than a border on it, since a border changes what the layout gave the control and a control that grew when the keyboard reached it would move the page.

- [x] **AU7. Every drawn control answers the keys its own kind owns.** Space and return use a control, the arrows walk a set, and the arrows move a value — in the opposite sense from the one they walk a set in, which is what every system does and what a reader expects of each. The first attempt had a stepper going down when the up arrow was pressed, because a set and a value were sharing one mapping. None of it is a renderer's business, so the behaviour is the same on all three.

- [x] **AU8. A pointer's second button.** `onContextPress` carries where it happened, raised by a secondary click and by a finger held, which every platform means one thing by. Where it happened is what a menu is drawn at, and on Android a long click carries no position at all, so the box records where the touch before it landed.

- [x] **AU9. The progress family, drawn.** A straight bar, a round one and a spinner, all three drawn as runs of straight lines rather than as rotating boxes — a box cannot be an arc of part of a circle. An indeterminate bar is a band that travels and an indeterminate circle is an arc that turns.

- [x] **AU10. A second shadowed case, this time in Swift.** Adding focus to the iOS renderer put a second `case "onFocus"` above the one that had always been there, which Swift warns about and nothing failed on. `promises.shadowed()` reads the iOS switch now alongside the browser renderer's run of checks and the Android `when`, and it caught a real one in the browser renderer in the same run — an `autoFocus` branch added above the one that already handled it.

### What this round did not finish

- **A drag, and the slider that needs one.** Still the platform's under every control theme.
- **The field**, the date and time pickers, and the colour picker.
- **The components that are Lua and read no control theme** — the tab bar, what is shown over a screen, the chips and badges, and the furniture of a list.
- **The controls that are not here at all** — a floating action button, a navigation rail, a snackbar, a banner, a popover, pagination, a progress stepper, swipe actions on a row, and a tree.
- **The performance budget** for a screen of drawn controls.

## AV. The rest of the controls, and what every one of them owes

Section AU opened the control theme and gave the drawn controls a keyboard. This round is the rest: the drag a slider needs, the controls still handed to the platform, and the nine a reader meets on a phone that this library had none of. Every control drawn by the engine now keeps the same promises rather than each keeping what it happened to be written with.

- [x] **AV1. A drag, which `docs/events.md` had listed as deliberately not built.** The reason it gave was real: a drag inside a scrolling surface has to be arbitrated, and the three platforms arbitrate differently. `onPanStart`, `onPanMove` and `onPanEnd` carry `{ x, y, dx, dy }` against the box's own origin, and `panAxis` says which axis the box claims so the surface under it keeps the other. iOS claims with a recogniser that refuses to run alongside a scroll and gives the drag up when the finger goes the other way, Android with `requestDisallowInterceptTouchEvent` once the finger passes the platform's own threshold, and a browser with a captured pointer and `touch-action`. A pinch stays unbuilt, with the reason written down.

- [x] **AV2. The slider, and the range.** A track, the part of it that is filled, one thumb or two, following the finger through the drag and the arrows through the keyboard. Where the finger is on the track is what it is worth rather than how far it has travelled, which is what every slider does: a finger landing halfway along asks for the middle. A range is its own control, since a `UISlider` holds one value and the Android range slider belongs to a library this renderer does not depend on — the thumb the finger took keeps the drag, so crossing the other one does not swap them.

- [x] **AV3. The progress family, the card and the tooltip.** A straight bar, a round one and a spinner, all drawn as runs of straight lines rather than as rotating boxes. A card and a tooltip are chrome and nothing else, so both follow the control theme entirely.

- [x] **AV4. The field, which stays half the platform's.** `TextInput` is the editing and nothing else, which is what a screen drawing its own box around one wants. `TextField` is the box: the container, the outline and what focus does to it, the label and where the design puts it — Material 3 floats it into the outline, Material 2 raises it above, Apple's writes it beside — the helper line, the error state and the parts at either end. Making `TextInput` itself the chrome was tried and reverted: it moved the host node a level deeper and broke the keyboard's own tests, which are about a real behaviour rather than a shape.

- [x] **AV5. Nine controls that were not here at all.** A floating action button in its three sizes, drawn as a round filled button under `cupertino` since Apple's system has none and refusing would leave an application built around one with a hole in it. A navigation rail, which takes the same tabs a bar takes so a screen that changes shape changes one prop. A snackbar, which is what a toast is missing — a toast says something and a snackbar offers to undo it. A banner. A popover anchored to the frame the caller reports. Pagination, which draws a window of the numbers with a gap standing for what is left out. The numbered steps of a form. A tree of rows that hold rows. And swipe actions, drawn behind the row so the row slides over them.

- [x] **AV6. Every drawn control keeps the same promises, and a case reads all of them at once.** Each says what it is, is a stop on the way through with a keyboard, says when the keyboard has reached it, and answers the keys its own kind owns. It is read as a set rather than one control at a time, which is what found five that were reachable and could not be used, and two containers announcing themselves as the thing they hold: a segmented control and a navigation rail each said they were a tab, so a reader was offered a control that does nothing.

- [x] **AV7. What it costs, measured rather than assumed.** A screen of forty rows each holding a switch is 121 nodes under `native` and 221 under `material3`, and laying it out again takes 4.4 ms against 4.5 ms — eighty per cent more nodes for two per cent more time. The budget holds both that and the operations one press sends. Nothing about the engine limits this, which is the question that was open.

## AW. Every control the control theme shapes

The rounds before this drew the controls a design changes most. What was left was everything else: the date, time and colour pickers, and the components that were already drawn by the engine and took their shape from the look alone — a tab bar whose indicator is the difference between two design systems, everything shown over a screen, the chips and badges, and the furniture of a list.

- [x] **AW1. The tab bar reads the control theme.** Where the label sits against the icon, how tall the bar is, whether there is a rule above it, and the indicator — Material 3 draws a pill behind the icon of the chosen tab and Apple's system draws nothing at all — are the design's. A tab is a stop on the way through with a keyboard and the arrows walk the row.

- [x] **AW2. What is shown over a screen reads it too.** A modal, a sheet, an alert, an action sheet, a menu and a toast each took their corner, their ground and their shadow from a literal written six times. One helper answers all of them from the design, and the scrim is the design's as well. A design that rounds its panels to 28 points rounds all six.

- [x] **AW3. The chips, badges, avatars, skeletons and accordions.** Each is chrome and nothing else, so each is entirely the design's: a chip's corner and whether it is outlined, a badge's smallest size and its dot, an avatar's corner, a skeleton's corner and the height of one of its lines, an accordion's row and its chevron. A chip that can be pressed is now a stop on the way through, which it was not.

- [x] **AW4. The pickers.** A date is a month drawn as a grid of days with the months either side a press away, written as `YYYY-MM-DD` rather than as a number of seconds — which is what a screen holds, what a form sends and what reads the same everywhere. A time is two columns of numbers, written as `HH:MM` on a twenty-four hour clock, with how finely it may be chosen the design's to say. A colour is a palette rather than a wheel, since a colour chosen from a grid is one somebody designed. All three stay the platform's under `native`, where the system's own is what a reader knows.

- [x] **AW5. A list's separator and a carousel's dots.** The last of the furniture. What a design changes here is not the scrolling but what is drawn around it.

- [x] **AW6. A kind that no platform draws carries what it is drawn with, and `native` leaves it alone.** Eight kinds are like that now, and a control theme written before any of them existed is still complete. `native` skips them rather than handing them to a platform that has none of them, which was a control drawing nothing where it was written.

## AX. A validation, and five applications built after ones people already have

Two halves. The first read everything the three rounds before it built and asked whether any of it was actually reaching a screen. The second built five whole applications out of the library, each after the kind of product a reader already has on their phone, and let each of them say what the library was still missing.

### What the validation found

- [x] **AX1. A control the platform draws was being drawn by the engine anyway.** `Card` and `Tooltip` registered their kinds with a drawing of their own, which is what makes `native` leave a kind alone — right for a control no system has, wrong for one every system has. Both were drawn by the engine under every control theme, so the platform's own card and tooltip were never reached at all. Each is a kind with no default now and the three drawn themes carry an entry for it. Held by a case that reads sixteen controls under `native` and under `material3` and fails on one drawn the same way by both, which is the shape of the defect rather than the instance of it.

- [x] **AX2. Every control draws under every control theme.** Sixteen by four, each built and laid out, none raising.

### The five, and what each of them needed

Each is a whole application: a food delivery, a ride hailing, a marketplace, a messaging application and an audiobook player. What makes one of these read as the real thing is the density, the proportions and the order things come in rather than the colour, so the copy is of the shape and never of the name. `docs/sample.md` says what each is built around and `gui/tests/apps_test.lua` walks all five.

- [x] **AX3. A subtree could not be put in a look of its own.** An application wears one look and the only way to change it was to change the runtime's, so five applications in one gallery was five palettes that could not coexist. `gui.Look` draws everything under it in another look and leaves the rest of the application in its own.

  Every colour, every spacing step and every corner is resolved on the way out of the runtime rather than by anything a screen carries, so this is the runtime knowing which look governs which node. The index walk it already makes on every commit stamps each node with the look in force, and what resolves a style reads that instead of the application's — no second walk, no per-node lookup, and a node whose stamp changed marks the tree to be painted again, so a `Look` whose value changes reaches everything under it without any of them rendering. It is the other half of `gui.Controls`, which has done the same for the parts a control is built from since AU.

- [x] **AX4. A stack was all one header or all the other.** `hidesBar` and `barStyle` belonged to the stack, so an application was either entirely under the platform's bar or entirely without one. Nearly every application on a phone is neither: a first screen carrying a band of its own and detail screens under the platform's bar is the shape three of these five have. Both are a screen's to say now, beside the `titleView`, `trailing`, `largeTitle`, `scrolled` and `transition` a screen already carried.

- [x] **AX5. A field carried a box of its own on two platforms out of three.** An application draws a search pill and puts an editable run inside it. On the web and on Android the run arrived with the user agent's border, ground and padding, so the pill had a second box sitting in it, and on iOS it did not — the same screen was two different screens. What the platform owns is the caret, the selection, the keyboard and every input method for a language that needs one, and the box around them belongs to whoever wrote the screen, which is what `TextInput`'s own default style has always said. The web renderer's comment already promised exactly this and the code only did it for a button.

- [x] **AX6. Fourteen marks the set did not carry.** A bag, a cart, a barcode, a filter, a microphone, a paperclip, a phone, a video camera, a shield, a rewind, a forward, a bulleted list, a double check and a headset. A messaging application whose composer has no microphone and a marketplace whose search has no barcode are not copies of anything. The gallery draws the whole set out of `icons.names()`, so each of them appears there without being listed anywhere.

- [x] **AX7. A list of children spread anywhere but last.** `table.unpack` in the middle of a table constructor yields one value rather than all of them, so five cars written before a button is one car and a button — no nil, no error, and nothing on screen wrong enough to notice. It had already cost a stepper its keys and a checkbox and a radio their focus rings, and it took four rows off a ride screen here. `promises.unspread()` reads every Lua file under `gui` and `sample` and fails on a spread that is not the last thing written in its element, so it is a failing suite rather than a screen somebody eventually looks at.

- [x] **AX8. A page nothing linked to.** `docs/controls.md` was written, tested and reachable only by knowing its filename. The README index is what a reader arrives at, so the suite fails on any page in `docs/` the README does not name.

- [x] **AX9. Nothing is fetched and nothing is a photograph.** Thirty-three pictures are drawn by `tools/draw-scenes.py` from the shape of the thing each stands for, in the palette its own application uses, so a shelf of them reads as one catalogue rather than as a search result. The map under the ride screens and the wallpaper behind the bubbles are not files at all: each is a `gui.Canvas` worked out from the box it turned out to fill, so neither is a size to ship or a picture to scale. The sample carries no network and no licence.

- [x] **AX10. No real name and no real mark.** The check that held the demos to that read thirty-two names as runs of letters, which meant a paragraph about wrapping text failed it. It matches whole words now, and the list covers the products these five are built after.

- [x] **AX11. The guidelines caught the marketplace twice.** Its own header was forty points where a finger needs forty-four, in the search field and in the two marks beside it. A dense application is dense in its spacing and not in what a finger has to land on.

- [x] **AX12. A slider was a third of the width it had, and its thumb never left the left end.** Both found by looking at a screen the applications had put a slider on, and neither is anything a tree-based case could see: the engine sent the right frame and the right value every time.

  A range input is 129 points across until something says otherwise and takes whole numbers until something says otherwise, so a slider running from nought to one could only ever be at either end — four tenths was rounded to nought and stayed there. The step is now set when the element is built, since a slider the tree gave no step to is continuous, which is what every platform's own slider is.

  The width is the deeper of the two. A slider and a segmented control each run the width of the row they sit in, and each answers a width of its own when a platform is asked how large it draws one — a browser says 129 and 88, UIKit answers `noIntrinsicMetric` for both. So the engine believed one platform and not the others, and the exception that hid it was written inside one renderer for one control. Which axes a platform decides is the declaration's to say: `natural.platformHeight` takes the height and leaves the width to the row, `Slider` and `SegmentedControl` name it, and the renderer's exception is gone.

- [x] **AX13. The stand-in was agreeing with the exception rather than modelling a platform.** The headless renderer answered a width of nothing for a slider and for a segmented control, which is what the web renderer's special case produced rather than what any platform says, so the case that held the rule was really asserting the stand-in — and it passed throughout. It answers what a platform answers now, the case asserts that the width is dropped rather than that it was never offered, and the browser suite holds the whole of it where the defect actually lived.

- [x] **AX14. A picture of the screen an application opens on says nothing about the screens behind it.** Every application in the gallery had exactly one screenshot per appearance, of the screen it opens on, and the rule this project keeps is that a screen is proven by looking at it. A demo may name a walk now — what to press to reach each screen inside it and what to file each picture under — and the browser follows it. What that found in one pass: a restaurant cover drawn as the place's own square logo stretched across a banner, two rows of carousel dots where the carousel already draws its own, a menu whose dishes ran together with no rule between them, a number plate wrapped onto two lines, a paperclip that came out as an O, and the slider above. Every one of them passed the tree-based suite.
